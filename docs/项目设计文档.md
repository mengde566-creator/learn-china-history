## 1. 立项依据：痛点 → 设计回应

你在第 1 轮全选了七个痛点。这不是问题，但意味着必须把它们**排出层级**，否则每个都做不深。

| 痛点 | 层级 | 由什么解决 |
|---|---|---|
| 原文太枯燥，读不下去 | **动机层（最优先）** | 沉浸叙事：场景把你拉进去 |
| 读的时候懂了，过几天全忘光 | **留存层** | 记忆层：复习卡 + 对话记忆 |
| 事件前因后果、时间顺序理不清 | **结构层** | 场景链 + 因果链 + 时间轴 |
| 人物太多，谁是谁、什么关系记不住 | **结构层** | 人物卡 + 关系图谱 |
| 地理方位、行军路线搞不清 | **结构层** | 地图层 |
| 制度、官名、礼制等背景缺失 | **背景层** | 随场景出现的背景卡 |
| **文言字词、句读读不懂** | **降级处理** | 见下方说明 |

### ⚠️ 关于"读不懂文言"：你的澄清改变了它的地位

你原本把这一条排在最前面。但第 3 轮你澄清了：

> "我重点是学习这些历史，并不是要去应对考试，所以应该是白话文为主，但可以随时去查看历史原文。"

这意味着：

- **你的学习目标是"读懂这段历史"，不是"读懂古文"。**
- 原文的地位从"学习终点"变成"权威底本 + 查证手段"。
- 因此**不需要**逐字注音、逐词训诂、句读训练——那是应试工具的做法。
- 需要的是：**白话讲透 + 关键原文可随时展开 + 名句保留原貌**。

**这个转变让项目大幅简化，也更聚焦。** 如果后面你发现自己其实想要古文能力，这是一次可回退的设计决策（原文层已经是独立模块）。

## 2. 产品定位

### 是什么

一个**以人物对话为核心机制**的历史沉浸学习产品。你进入一个历史场景，场景里的人会开口，你可以问他，问出来的东西牵出史料、背景、地图和因果。

### 不是什么（重要的边界纪律）

| 不是 | 原因 |
|---|---|
| 古文学习 / 应试工具 | 见 §1，目标是懂历史不是懂文言 |
| 通史 / 百科 | 只做荆轲，做透 |
| 《史记》全文数据库 | 只保留与场景相关的原文段落 |
| 游戏 | 没有胜负、没有养成、没有数值 |
| 影视化历史剧 | 一切推演都必须能回溯到史料依据 |

### 差异化

市面产品分两类：**精读器**（注释好原文，你读）和 **知识图谱 / 时间轴**（史实结构化，你看）。

**没有人做"你跟荆轲说话"。** 这是这个项目的立足点。

## 3. 核心体验：主循环

```
① 进入场景
   └─ 环境铺陈：时间、地点、在场的人、此刻的局势
        │
② 场景活起来
   └─ 人物开口。台词优先从原文词句化出
        │
③ 你开口问  ←──────────┐
   └─ 从**预置问答**里挑一条   │
        │                │
④ 随时展开「依据」       │
   └─ 哪句是《史记》原文？哪句是推演？推演基于什么？ ──┘
        │
⑤ 场景结束
   └─ 回到原文：这段场景对应的原文段落，此刻每个字都认识了
        │
⑥ 沉淀
   └─ 复习卡 + 关系/地图更新
```

> ⛔ **③ 已改（2026-10-17）**：原文写的是「你开口问 → **AI 以人物身份回答**」。
> **AI 自由对话不做**，所以这一步现在是**从人工审校过的预置问答里挑**——
> 产品里没有输入框，读者看到的是问题清单（`SeedSheet`）。
> 「用户不一定按顺序问」这件事仍然成立：清单按分组排，他挑哪条都行。

**关键设计决策**（你已确认）：

- **主干 = 沉浸叙事**。精读、地图、关系图、测验都不是并列功能，而是从主循环上长出来的枝叶。
- **史实边界 = 先入戏，但随时可查依据**。不打断沉浸，但你不会被骗。
- **用户不一定按顺序问。** 他可以问任何问题，包括"这一切值得吗"这种史书没写的东西——系统负责告诉他这是推演。

> ⚠️ **上一段第 3 条要按新范围读**：「可以问任何问题」现在是
> **预置清单覆盖到哪些问题**。清单之外的问法没有入口——所以种子的覆盖面就是产品的边界
> （`content/README.md`「已知缺口」里挂着这一条，等真的被人用过一轮再评）。

## 4. 内容范围：第一个垂直切片

### 4.0 层级（2026 修订）

原设计只有两层（总览 → 场景），因为当时只有荆轲一个人。
但要容纳**曹操、刘裕、高欢、宇文泰**这些人，且**每人有数十上百篇故事**，必须重新分层：

```
时代（分组标签，不做成一级页面）
  └ 人物        荆轲 · 曹操 · 刘裕 · 高欢 · 宇文泰 …
      └ 故事    每人 7 ～ 上百篇
          └ 情节点   故事内部，不导航、不编号
```

**三个决定，以及理由**：

| 决定 | 理由 |
|---|---|
| **「时代」只是分组标签**，不是一级页面 | 只有 5 个人时它是个空层，50 个人时才需要独立成页。做成标签，两种规模都成立 |
| **「阶段」可选**，放在人物页内部 | 荆轲只有 7 篇，直接列就行；曹操上百篇才需要按「起兵 / 鼎盛 / 晚年」分组。在 `stories.md` 里用 `## 阶段名` 分段即可 |
| **「情节点」不是层级** | 它是拆解故事时的工具。**界面上不出现**——分镜表上的词不该出现在易水边 |

**术语统一**：原设计叫「场景」，现统一为「**故事**」。用户说的是故事，不是场景。

**目录随之改为按人物分组**：

```
content/people/<person>/
  person.md  source.md  stories.md  cast.md
  stories/<id>.md   seeds/<id>.md   cards/<id>.md
  gloss.md   gloss-parts/          ← 2026-10 后加的：逐段直译（完整资料页用）
  assets/                          ← 图片
```

**加一个人 = 加一个目录**，不动任何现有文件。

**路由**：

| 路径 | 页面 |
|---|---|
| `/` | 总览（按时代分组的人物） |
| `/p/[person]` | 人物页（他是谁 / 为什么读他 / 故事列表 / 关键时点） |
| `/p/[person]/[story]` | 故事页（原「场景页」） |
| `/p/[person]/source` | **完整资料页**（全篇底本 ＋ 逐段直译）——**设计时没有这一页，2026-10 加的** |

> ⚠️ **`cast.md` 是可选的**：荆轲有，曹操那十篇没有。缺了不报错。

| 7 | **图穷匕见** | 差在哪里 | 「王负剑！王负剑！」「断其左股」 |

★ **首做场景 = 6 易水送别**，作为垂直验证。

> 🕘 **历史（M2 的计划）**。选它的理由和后面的「M2 只做一个场景」都是当时的判断。
> **实际进度（2026-10-17）**：荆轲 8 篇、曹操 10 篇都已实现，
> 早已超出"只做一个场景"的验证范围；「场景」也统一改叫**故事**。

选它的理由：
- 你自己就举了这个例子（"可以在易水送行时问荆轲此去心中所想"）
- 自包含：不依赖前序场景也能独立体验
- 画面感最强，情绪峰值最高
- 在场人物少（荆轲、高渐离、太子丹、送行者），人物扮演难度可控
- 原文只有几句，但句句是名句
- 时长约 15 分钟，符合"电脑前坐下来学半小时"的场景

**M2 里程碑只做这一个场景，跑通全循环。** 一个场景跑通，胜过七个半成品。（🕘 历史）

### 荆轲故事的完整原文规模

《史记·刺客列传》荆轲部分约 1500 字。按 §7 的压缩原则处理后，实际需要人工审校的内容约 **300–400 条内容对象**。以你每周 1–2 小时的投入计，这是 2–3 个月的内容工作量。

> 🕘 **历史**：这句话原来还有一个括注「（AI 生成初稿，你只做"有没有说错"的判断）」。

> 实际的量也不再需要估：`npm run check` 会按人物、按篇报出当前的段数、种子数、复习卡数。

## 5. 功能模块

### 5.1 故事（原叫「场景」，Scene）—— 产品的核心单位

> 📝 **术语**：设计时叫「场景」，§4.0 起统一改叫**故事**；代码里也是 `story`
> （`/p/<person>/<story>`、`stories/<id>.md`）。**本节以下仍用设计时的说法**，读作"故事"。

一个故事 = 一个可以独立进入的戏剧单元，预期时长 **10–20 分钟**。

**进入之前**：一屏情境铺陈（时间 / 地点 / 局势 / 在场的人）。文字尽量短，负责建立代入感。

**故事中**：
- 人物按情节点推进开口，不强制你线性阅读
- 你随时可以展开「依据」、跳到「原文」、离开
- 侧栏始终可以切到：这一篇的原文 / 背景卡 / 依据映射表

**故事后**：
- 复习卡（默认折叠，点开才看答案）——**数量由内容决定，不是固定 2–3 张**
- 提问入口「你想说什么」：从预置问答里挑（原来这里是自由输入）
- 回到原文，此刻原文不再是天书

> 📌 **「你在这里问过什么」回顾没有实现**：阅读推进和复习状态是 R12 的范围（本地存储）。

### 5.2 人物对话 —— ⛔ **AI 扮演已取消**（2026-10-17）

> **这一节原来是「本项目的技术核心」：让模型以人物身份即席回答，用知识边界约束它。**
> **现在不做。** 用户 2026-10-17 明确：不做 AI 自由对话——不开发生成式对话、自由输入、
> 模型接入、API key 配置、能力探测、额度计费、提示词防护。
>
> **替代它的是静态预置问答**（`content/people/<id>/seeds/<id>.md`）：
> 每一篇一份人工写、人工审校的问题清单，每条带一个标记和一个「依据」。
> 它本来就是学习资料，不是"AI 的降级方案"。
>
> **下面这张表还留着，因为它对写内容的人仍然有用**——写任何一条预置回答之前，
> 都要先回答同一组问题。只是「知识边界」现在**不是提示词，是写作纪律**：
> 写错了没有模型去兜，只有审校和闸门。

**每个角色必须携带以下字段**，否则会写错：

| 字段 | 作用 | 荆轲·易水送别示例 |
|---|---|---|
| **身份** | 他是谁 | 卫人，游历至燕，太子丹尊为上卿 |
| **知识边界·已知** | 此刻他知道什么 | 秦已破赵、兵临燕境；太子丹待他甚厚；此去九死一生 |
| **知识边界·未知** | 此刻他**绝对不知道**什么 | 他自己会失败；秦王会绕柱；燕国终将灭亡；高渐离日后以筑击秦王 |
| **语言风格** | 他怎么说 | 沉静、寡言、不辩解；称谓用"足下""太子" |
| **史书台词** | 原文里有的话（**不可改动**） | 「风萧萧兮易水寒，壮士一去兮不复还。」 |
| **可推演范围** | 哪些可以自己写 | 他的心理活动、对太子丹的真实看法、对失败的预感 |
| **不可触碰** | 越界即出错 | 任何公元前 227 年秋之后的信息 |

**防说漏嘴**：知识边界是硬约束。荆轲的条目里绝不能出现"我死后高渐离会去刺秦王"——哪怕这很有戏剧性。
（这份清单落在 `people/jingke/cast.md` 的「禁」一档，见 `content/README.md`「知识边界：三档」。）

### 5.3 依据层（"先入戏，随时可查"的具体设计）

**每条回答**（现在是预置问答里的每条；原来是"每条 AI 回复"）下方有一个**极轻的标记**
（一个细点或细线，默认不显眼）。点击展开：

```
┌─ 这条回答的依据 ─────────────────────┐
│ ◆ 出自原文                            │
│   《史记·刺客列传》第二十六           │
│   「风萧萧兮易水寒，壮士一去兮不复还」 │
│   [展开完整段落]                      │
│                                       │
│ ○ 合理推演                            │
│   推演自：荆轲受命时的沉默（原文仅记   │
│   「荆轲曰：此国之大事也」），以及对   │
│   太子丹催促的反应（「荆轲怒」）       │
│                                       │
│ △ 存疑                                │
│   史书未载。以下为后世的推测与评价。   │
└───────────────────────────────────────┘
```

**标记的含义**（详见 §12.6；原来是四类，**现在是六个**）：

- ◆ **出自原文**：可逐字核对
- **◇** **出自小说或野史**：出自底本正文之外的另一本书（《三国演义》等）——**不是史书，也不是"更不可靠的 ◆"**
- ○ **合理推演**：史书没写，但从史书有写的部分能合理推出。必须说明推演链条
- △ **存疑**：史书没写，**后世有争议**。列出主要说法
- **—** **史书的沉默**：史书没写，**且无法推演**。直接告诉用户"这里没有答案"
- **ⓘ** **产品说明**：这一条回答的是产品本身，跟史料无关（2026-10-14 补的第六个）

默认全部收起。**沉浸优先，但账随时可查。**

### 5.4 全景层（从主循环延伸的枝叶）

> 📌 **未实现（2026-10-17）**：下面三个视图在代码里**一个都没有**。
> 现在有的三个全景视图是故事页侧栏的「原文 / 背景卡 / 依据映射表」，
> 以及人物页的「完整资料页」（`/p/<person>/source`）。这一节是待做项。

三个可随时切入的全景视图，不需要按顺序看：

| 视图 | 回答什么问题 | 呈现方式 |
|---|---|---|
| **地图** | 在哪？怎么走的？ | 静态底图 + 热点，点击看古今地名对照 |
| **人物关系** | 谁和谁是什么关系？ | 预布局的关系图，边标注关系类型与依据 |
| **因果链** | 为什么打？打完怎样？ | 事件节点 + 因果箭头，可点击回到对应故事 |

**注意**：这三个视图是"枝叶"。它们服务于主循环，不独立成章。首版可以只做**地图**和**人物关系**。

### 5.5 记忆层（复习）

- 读完故事复习 N 张卡（**每篇有多少张由内容决定**，`npm run check` 会报）

### ⚠️ M1 的实际格式决定：Markdown，不是 YAML

上面的例子是 YAML，但 M1 实际交付的是 **Markdown**。理由：

> **M1 的唯一目的是被审校。格式必须服务读者，而不是服务未来的代码。**

如果交给非程序员一个 700 行的 YAML，结果是打开、看到缩进、关掉——M1 就白做了。内容项目最常见的死法不是写不出来，是**写出来了但没人真的读过**。

Markdown → YAML 是纯机械转换，M2 需要时再做。**单一数据源的原则不变，只是这一阶段的"源"是 Markdown。**

由此得到一条通用规则：**内容格式的选择，取决于这个阶段谁在读它。**

## 7. 叙事压缩原则

你举的例子（"悼文可以简化为 A 为 B 写悼文，说 B 生前忠孝、立下多少功绩"）是本项目最重要的内容规范之一。固化为规则：

### 必须保留原貌

- 推动情节的句子
- 塑造人物的关键话语
- 后世流传的名句（「风萧萧兮易水寒」）
- 冲突最尖锐处的对话

### 压缩为一句话概述（原文可展开）

- **程式化文书**：诏令、奏疏、盟书、悼文、檄文
- **重复性对话**：同类劝说、同类推辞
- **礼仪流程**：繁复的朝见、祭祀、丧葬程序
- **同类事迹罗列**：多处战功、多位同类人物

### 压缩的呈现方式

```markdown
太子丹在易水边为荆轲送行，众人皆着白衣白冠。

> ▸ 展开原文（3 句）
```

概述在前，原文在后，默认收起。**读者永远知道原文在哪，但不必被它挡住路。**

### 压缩的红线

**不得改变事实。** 概述只能省略细节，不能添加原文没有的信息，也不能改变因果方向。"简化"不等于"改写"。

## 8. 内容生产流程

> 🕘 **历史（设计阶段的设想）**：下面的流程图假设「AI 承担全部初稿工作，你只做判断题」，
> 并且有「AI 重写」这一步。**AI 现在不参与写作，也不参与产品**（2026-10-17）。
>
> **现在的流程（以代码为准，见 [`../content/README.md`](../content/README.md)「加一篇故事要做什么」）：**
>
> ```
> ① 在 stories.md 的「故事一览」加一行（篇名、情境、时间、原文范围）   （人）
>         ↓
> ② npm run new-story -- <人物> <篇>   生成骨架：门口、逐行依据、情节点、映射表
>         ↓
> ③ 填白话、背景卡、在场人物                                          （人）
>         ↓
> ④ sources 里没有的句子用 npm run ref-grep 从参考文本里找，抄进去     （人 + 工具）
>         ↓
> ⑤ npm run check ＋ npm run check-sources                            （机器闸门）
>         ↓
> ⑥ 交给人读一遍（`content/README.md`「一篇故事该满足什么」第二栏）    （人）
> ```
>
> **第 ①–③ 步的性质没变**：人只做判断，机械的串线交给工具——
> 只不过那个"工具"是 `scripts/new-story.mjs`，不是一个模型。

你的投入是 **1–2 小时/周**，只做"读并挑错"。

```
① 拆解      从原文提取事件、人物、原文锚点        （人，一次性）
        ↓
② 生成      故事文本、人物卡知识边界、预置问答     （人 + 骨架工具）
        ↓
③ 审校 ★    你读，只回答一个问题：              （你，1–2h/周）
            "有没有说错？"
            说错了 → 标记 → 改内容
        ↓
④ 固化      审校通过的内容变成静态内容            （系统）
        ↓
⑤ 验证      你和朋友实际体验，记录卡住的地方      （你 + 朋友）
```

**审校的操作要求**：你不需要写任何东西，只需要在内容上标「这里不对」或「这里我没看懂」。降低门槛是让流程能持续的关键。

**分工的性价比**：初稿 + 人工挑错的组合，比"你来写"快得多，比"不审"可靠得多。

七个场景一起做，如果核心循环不好玩，你会在做完七个之后才发现。只做一个场景，你可以在两小时内知道自己到底喜不喜欢这个产品。**先验证心脏，再造四肢。**

> 下面这批要求（ⓘ 层去事实化、输入侧未来内容检测、用户身份固定、禁项分层、
> 模态层/确认层/时态层、纪元层、元史料层、虚构层、已死／不在场、锚点后移＋TTL、
> 以及"12 条攻击跑 5 次"的验收）**都是针对模型的，不适用了**。
>
> **但红队提出的史实问题本身没有消失**，它们换了归属：
>
> | 红队指出的 | 现在归谁管 |
> |---|---|
> | 「禁」清单按人分散、覆盖不一致 | 写作纪律：`cast.md` 的「禁」一档 ＋ 每篇的映射表 |
> | ⓘ 层不许放未来事实 | 内容规则：`ⓘ` 只能写产品说明（`content/README.md` 六个标记） |
> | 纪元层（公元纪年是后世换算） | 内容规则：公元年份一律 `○ 外证`，不许挂在 ◆ 底下 |
> | 「已死／不在场」的角色 | 内容规则：不在场的人不进本篇问答 |
> | 元史料层（"你被后世写进书里"） | 内容规则：这类问题用 `—` 或 `ⓘ` 正面交代 |
> | 说错的代价 | 编译闸门（`npm run check`）＋ 逐字核对（`npm run check-sources`）＋ 人工审校 |
>
> 保留在下面，是这份复核的历史记录。

独立红队对「禁」清单做了 12 条攻击测试，结论是：**它目前不是一套可运行的边界，是一份未完成的草案。**

**12 条里至少 3 条被判定为"必然突破"**，另有多条结构性缺陷。以下为 M2 必须处理的项：

#### 一、验证场景要扩

> **易水送别是七个场景里边界最松的一个。** 在场人物的禁项几乎全是"会不会成功"，而这个问题在送别场景里天然可以被悲壮化。**用它做垂直验证，会系统性低估这套机制的难度。**

M2 验证集必须至少补两个角色扮演测试：**场景 7 的秦舞阳**、**尾声的高渐离**。

#### 二、架构级修改（不是文案能解决的）

| 项 | 原因 |
|---|---|
| **ⓘ 层去事实化 ＋ 不进模型上下文** | ⓘ 原写着「荆轲卒于公元前 227 年」，把未来事实放进了**同一段上下文**，用户零成本反喂。**这是产品自己制造的泄露。** M2 需改为前端注入，且不含具体年份／事件名 |
| **输入侧未来内容检测** | 唯一能封住"确认式泄露"的办法。命中未来内容时不投给角色，直接走系统层 |
| **用户身份固定** | 现有 prompt **从未规定"你"是谁**。一旦模型承认对方来自后世，禁清单的前提就从"他不知道未来"变成"他知道但不能说"——后者脆弱得多 |

#### 三、内容结构补充

| 项 | 原因 |
|---|---|
| **场景级未来事实登记表**（全角色禁项并集） | 禁项按人分散导致同一事件覆盖不一致：「秦舞阳色变」在荆轲卡有、太子丹卡没有 |
| **「禁」加三层**：模态层／确认层／时态层 | 现有 13 条是**事件枚举**，挡不住 9 类非事件路径——概率、预感、确认、纠正、假设、元问题、纪元、史料、虚构 |
| **纪元层禁项** | 公元纪年确立于公元 6–8 世纪，晚于荆轲约七百年。而场景头与 ⓘ 层到处是"公元前 227 年" |
| **元史料层禁项** | 《史记》《刺客列传》、司马迁、汉代，**一条都没禁**。用户以"你被后世写进书里"施压时规则完全空白 |
| **虚构层规则** | "你是 AI 吗"被追问时怎么办——设计文档只在**视觉**上决定了不做聊天窗，**没有任何 prompt 规则** |
| **已死／不在场规则** | 田光（`025` 自刎）、樊於期（`046` 自刭）在场景 6 都是死人，原稿无此字段 |
| **锚点后移 ＋ TTL** | 现有禁项没有失效条件。到了场景 7，「秦舞阳色变振恐」正在发生，该条会反过来禁止他说出**自己正在经历的事** |

#### 四、验收标准

**把红队那 12 条攻击直接做成回归用例：每条跑 5 次，任何一条突破率 > 0 即不通过。**

#### 五、红队明确说修不了的部分

> 「**确认式泄露**（模型顺从性）和**沉默式泄露**（拒绝回答本身就是答案），在纯 prompt 层面我认为**无解**，必须靠输入侧拦截或前端兜底面板。」

**愿意说"这里我修不了"的复核，才值得信它说"这里能修"。** 这一条应作为 M2 的架构前提，而不是留到上线后再补。

## 12. 视觉与交互规范

> 可运行样张：[`design/style-tile.html`](../design/style-tile.html)（设计稿，非产品）

### 12.1 核心命题

屏幕上永远同时存在两个世界——**「入戏的场景」和「可核查的史料」**。它们必须一眼可分，又不能割裂。

整个视觉系统围绕这一个问题构建。

### 12.2 双面：明暗即语义

| 状态 | 视觉 | 含义 |
|---|---|---|
| **场景态** | 暗场（玄 `#101318`），文字如自暗中浮现 | 入戏 |
| **依据态** | 场景退后变暗，侧栏转为纸面（纸 `#F7F4EC`） | 查账 |

**产品的核心理念直接变成视觉本身**——不需要任何说明文字，用户第一次点开依据就懂了。

需提供全局浅色开关，照顾长时间暗色阅读的疲劳。

### 12.3 色彩母题：易水

| 名 | 值 | 用途 |
|---|---|---|
| 玄 | `#101318` | 暗场最底 |
| 素 | `#ECE7DD` | 白衣冠 · 暗场文字 |
| 纸 | `#F7F4EC` | 查账面 |
| 苍 | `#7D9AA8` | 易水之冷 · 你的声音、合理推演 |
| 朱 | `#B8402F` | 朱批 · 原文依据、重点 |
| 赭 | `#A97C4A` | 竹简之暖 · 存疑、古籍模式 |

取「易水」的冷 ＋「白衣冠」的素 ＋「朱批」的红。朱批在传统中即校勘与批注之色，**正好对应"查账"这个动作**。

### 12.4 字体即语义

| 字体 | 代表 | 出现处 |
|---|---|---|
| **宋体** | 那个时代 | 叙述、原文、人物台词 |
| **楷体** | 你 | 你的提问、心声 |
| **黑体** | 工具与考据 | 依据面板、标注、UI |

扫一眼就知道**这句话是谁说的**。

### 12.5 无框浮现

人物开口时，文字从场景叙述中直接浮现——**没有气泡、没有头像、没有聊天窗边框**。

理由（**现在更成立**）：一旦做成聊天窗，你就是在跟一个系统说话，而不是跟荆轲说话。
**而且产品里根本没有聊天这件事**——读者看到的是预置问答清单（`SeedSheet`），
选一条，回答浮现。这条视觉判断因此不需要再跟任何模型行为协调。

浮现动效：`blur(7px) → 0` ＋ 上移 12px ＋ 淡入，1.4–1.5s，缓动 `cubic-bezier(.2,.7,.3,1)`。

### 12.6 标记与入口预告（**现在是六个**）

| 标记 | 色 | 含义 | 要求 |
|---|---|---|---|
| ◆ | 朱 | 出自原文 | 可逐字核对（**含注**，书名跟着显示） |
| **◇** | **紫** | 出自**小说或野史**，不是史书 | 必须写出书名。**不在史料那把尺子上** |
| ○ | 苍 | 合理推演 | **必须展示推演链条**，不能只给结论 |
| △ | 赭 | 存疑 | 史书未载且**后世有争议**，列出主要说法 |
| **—** | 灰 | 史书的沉默 | 史书未载，**且无法推演**——直接告诉用户"这里没有答案" |
| **ⓘ** | 中性灰 | **产品说明**：这一条回答的是产品本身 | **不在史料那把尺子上**，跟史料无关 |

> ⚠️ **设计时只有四类；现在六个。** `◇` 是 2026-10-14 前后为了"演义不是史料、
> 但也不是更不可靠的 ◆"分出来的，`ⓘ` 是同一时期补的第六个。
> 完整定义、判据和色值以 [`../content/README.md`](../content/README.md)
> 「标记不止四个（现在是六个）」为准；色值以 `web/app/globals.css` 为准。

**入口预告设计**（解决"用户永远发现不了依据"的风险）：

每条回答后的「依据」入口会**显示这条回答里存在哪几类标记**。亮起朱色 ◆，就说明这里有可核对的原文。

**你不点开也知道值不值得点。** 入口本身成为信息。

**硬规则**：任何一条回答**必须**落在这六个之一。落不进去的，说明这条回答不该存在。

#### ⚠️ 第四档是复核后新增的

原设计只有三类。**但产品早就在用第四档了**——`04` 里"史书未载太子丹的言语"、`05` 的两道陷阱题，用的都是"史书的沉默"。

不拆开的后果：**△ 被拿来装"我们决定不回答"，从"史料有争议"退化成"产品不知道"**——而"知道哪些问题没有答案"正是这个产品的核心教学点。

拆开后两个标记各司其职：

| | 教给用户的东西 |
|---|---|
| △ | 这里有两说，**别当定论** |
| — | **有些问题没有答案** |

#### 事实层与台词层分开

人物**说出口的话**一律 ○（现代汉语改写，不可逐字核对）；支撑它的**事实**才标 ◆。

**只有原文原句直接进入回答时，台词层才能标 ◆**（如 `056`「风萧萧兮易水寒」）。

原稿在多处把整条回答标成 ◆，违反 ◆ 自身的定义（"可逐字核对"）。

### 12.7 古籍模式（可切换）—— 📌 未实现

默认横排简体保证可读性；一键切到**竖排繁体 ＋ 纸纹**，获得史料质感。

由此确立一条内容规则：**繁体只出现在古籍模式**。依据面板的引文一律简体，避免同一屏内繁简混杂。

> **现状（2026-10-17）**：没有古籍模式，代码里没有竖排／繁体的实现，
> **全库也没有繁体文本**（`content/README.md`「已知缺口」挂着这一条）。
> 现在只有 §12.2 的全局明暗开关（设置页「场景区浅色」）。
> 这条内容规则仍然有效：**内容文件里写简体**。

### 12.8 复习卡：问动机，不问年代

因为目标是理解历史而非应试，题目应问**为什么**：

- ✅「送行的人为什么都穿白衣、戴白冠？」
- ❌「易水送别发生在公元前哪一年？」

## 附：本设计的核心判断

如果这份文档只能留下三句话：

1. **这个产品的独特性在"你问荆轲，他答你"这件事上，不在任何其他功能上。**
   ——现在这句话的落点是**预置问答**：能问什么、每条答得站不站得住，就是产品的全部。
   所以种子的覆盖面和质量比界面重要。（原话是"你跟荆轲说话"，
   当时指的是模型即席应答；**那个做法已取消**，但"问—答"这个形态保留了下来。）
2. **最大的风险不是做不出来，是做出来了但教错了。**
   史料边界和原文锚点不是锦上添花，是生死线——
   现在靠三道：`npm run check`（结构与引文闸门）、`npm run check-sources`（逐字核对公版电子本）、
   人工审校。**没有模型可以怪，写错就是写错。**
3. **内容模型是地基，代码是装修。** 这一条被验证了：加一个人 = 加一个目录，
   加一篇故事 = 补几个数据文件（`npm run new-story` 生成骨架），**不动代码**。
