## 0. 这份规划要回答什么

1. **阅读进度**现在哪些能用、哪些是坏的（不是「还能更好」，是「坏了」）；
2. **收藏**在这个产品里是什么——它不是点赞，也不做「稍后再读」队列；
3. **朱批**（读者自己写的一句红字）挂在哪、怎么写得快、什么时候显示；
4. **书架**怎么把进度与收藏装进一页，并与「全部篇章」互相切换；
5. 四者共用的本机存储该怎么动，才不会在加第二个功能时把第一个搞坏。

一句话结论：

> 进度是**系统替你记的**，收藏是**你挑出来的**，朱批是**你自己写的**。
> 三者必须共用一层可靠的本机存储，但**不能共用一条清除命令、不能共用一个「最近」字段**。
> 现在的代码正好把第一件事的两半混在一起（§1.2 缺口 5）。

- **规模**：19 位人物、130 篇故事、129 个唯一篇 id、806 个情节点、每篇 2–12 段。

### 1.3 一个必须承认的前提

**没有跑 `npm run verify`、没有起浏览器、没有量过任何渲染耗时。** 下面对性能与交互的说法都是设计推断，实现时以实测为准。

## 2. 产品判断

### 2.1 三件事，三种「给未来的自己」

| 场景 | 读者心里的话 | 谁解决 |
|---|---|---|
| 被电话叫走，三天后回来 | 「我上次读到哪了？」 | **进度**：零决策，直接接上 |
| 读到一篇好故事 | 「这篇留着」 | **收藏**：一键存目 |
| 读到某段，有个念头 | 「这句我要记一笔」 | **朱批**：就地写一句自己的话 |
| 读完十篇，想知道走到哪 | 「我读了这么多了？」 | **进度**：轻量完成度，不做成就系统 |
| 读到一半不想读了 | 「先放下」 | **不是收藏**——「未读完」本身就是这个意思 |

第四行的取舍：**不做「稍后再读」队列。** 已经有「未读完」这个状态，再造一个 queue 会让读者每次都要先决定「这篇属于哪一类」。

### 2.2 收藏：篇级，一键（已定）

- **点一下就是收藏，再点一下取消。** 不弹窗、不填表、不问理由。
- 「不存在收藏一行还是一句」——收藏的对象**只有篇**，没有段落级收藏。
- 上一版把这里想成了点赞，于是担心「摩擦」；这个担心不成立：全库 130 篇，一个人一年收 10–30 篇，每一次都是有意的。**这里没有转化率要优化，只有「别收错」要照顾。**

### 2.3 朱批：写在右侧面板的「批注」页（已定）

它和收藏是两件事：

| | 收藏 | 朱批 |
|---|---|---|
| 对象 | 篇 | **情节点（段）** |
| 内容 | 一个时间戳 | **一句自己的话**（≤120 字） |
| 读者为什么按 | 「这篇值得回来」 | 「这里我有话说」 |
| 在哪看见 | 书架 | **右侧面板的「批注」页，跟着当前段** |
| 怎么找到 | 书架 | 段末「批注」二字变朱色 |

**不放在段后，因为会吃掉正文。** 批注一多，读者读的就是自己写的话，不是史书——这个产品的正文是书页，页边的东西不该挤进字里行间。这一点本项目已经做过一次同样的判断：人物介绍原本是段后卡，被否定后放进既有「人物」页签（`design/character-notes-2026-10-24/人物笺设计.md`）。批注走同一条路。

**页签本身就是分隔。** 上一版担心「读者的话混进史料会分不清哪句是谁写的」——那是把批注当成正文里的某种样式。开一个独立的「批注」页，点进去就知道这里全是自己写的；不点就看不见。结构上的区分比颜色上的区分可靠，这个担心不成立。

**它就是旁批。** 写在页边、与正文并读、不夹进正文——这正是「旁批」二字的意思，也是本项目书页旁批一路做下来的形态（`docs/书页旁批落地与滚动联动回归-2026-10-19.md`）。

**它不是笔记系统。** 没有标题、没有标签、没有富文本、没有引用块、没有图片。只有一个输入框和一句话。加任何一件，它就变成「要维护的东西」，而读者是来读史的。

### 2.4 书架：一个页面，两个视图（已定）

```
书 架                                   [ 我的 ]  [ 全部篇章 ]
──────────────────────────────────────────────────────────
接着读
  〈赤壁〉 曹操 · 读到 6 / 9                      →  继续
──────────────────────────────────────────────────────────
收藏 · 4 篇                     按人物分组，组内按收藏时间倒序
  曹操  〈赤壁〉 读到 6 · 朱批 2                    →
  曹操  〈官渡〉 已读完                              →
──────────────────────────────────────────────────────────
读过 · 12 篇                    在读在前（按最近），读完在后
  曹操  〈徐州〉 读到 3 / 9                          →
```

切到「全部篇章」是同一页的另一面：

```
[ 我的 ]  [ 全部篇章 ]
──────────────────────────────────────────
曹操 · 汉末三国 · 10 篇
  〈五色棒〉 3 段 · 未读
  〈刺董〉   6 段 · 读到 2 / 6 · 朱批 1
  〈赤壁〉   9 段 · 已读完 · ★ · 朱批 2
荆轲 · 战国 · 8 篇
  …
```

- **两个视图互切**，默认「我的」。切换状态放在客户端（`useState`），不写进 URL——故事页和书架页都是静态生成，服务端不读 query（§5.6）。
- **「我的」三个区块**：接着读 / 收藏 / 读过。读者写过的朱批**不单独成块**——写过批注说明读到了那一段，它必然出现在「读过」里；行上的「朱批 N」就是入口。
- **「全部篇章」是全书目录**，按人物分组（19 组、130 行）。它回答的问题和「总览」不同：总览选人，这里选篇。
- **空态**：一条记录都没有时，说「从总览挑一个人物，读起来就有了」，并给两个入口。不出现一个空白页。

### 2.5 五条产品原则

1. **收藏与朱批是读者亲手留下的东西，不能被「清阅读进度」顺手清掉。** 进度可重来，这两样重来等于丢掉读者花过的时间。
2. **不给新读者画假的「继续阅读」。** 没有进度就不出现这块（`design/next-reading-2026-10-23/设计说明.md` 已有这条纪律）。
3. **任何自动判断都要看得见。** 内容改版导致续读位置调整，入口必须说「这一篇更新过，从第 N 段接着读」，不能静默跳。
4. **不制造焦虑。** 不显示「你还有 87 条未读」，不做连续打卡，不做读完率排名。书架是架子，不是待办。
5. **本机就是本机。** 不做账号、不做云同步（`web/README.md:74-75`）。换设备唯一的诚实办法是导出／导入。

### 2.6 明确不做

| 不做 | 为什么 |
|---|---|
| 账号 / 云同步 / 服务端接口 | 与既有产品边界冲突 |
| 段落级收藏、名句摘录、自由划线 | 用户已定：收藏只到篇（§2.2）。摘录另行讨论，§4.3 已留位 |
| 富文本、标签、收藏夹、多级分类、图片 | 会让朱批变成「要维护的东西」 |
| 阅读时长、打卡、连续天数、读完率 | 假指标 |
| 复习算法（间隔重复、熟练度曲线） | 既有边界：不做记忆算法（`lib/progress.js:5-12`） |
| 公开分享页 | 没有后端 |

## 3. 功能设计

### 3.1 阅读进度 v2

| 位置 | 回答 | 形态 |
|---|---|---|
| 首页（新增） | 「我上次读到哪」 | 最多 1 条，有进度才出现：`接着读 · 曹操〈赤壁〉第 6 段` |
| 人物页（改造） | 「这个人我走到哪」 | 每张篇目卡一行：`读到 5/9`，读完的印「已读完」；顶部一行「10 篇，读完 3 篇」 |
| 书架「我的」 | 「我一共走到哪」 | 接着读 + 在读 + 读完（§2.4） |
| 篇内入口（保留） | 「从第几段接」 | 现有 CTA 不变，补一句 `已读到 5 / 9` |
| 读完（保留） | 「这篇收了」 | 现有读后区块不变 |

- **首页那条取 `at` 最新的一篇**，不是「最后打开的人物」。`last` 字段删掉。
- **完成度不做百分比**：「读完 3 篇」比「31%」诚实，不存在 0.7 篇。
- **`done` 是派生值**：判定一律 `beat >= beats`，存下来的只作兼容。现在 `verify-reading-progress.mjs` 正盯着「末段露出不算完读」，两处逻辑不能分叉。

### 3.2 收藏星标

| | 内容 |
|---|---|
| 按键 | 人物页篇目卡右侧、故事页标题右侧 |
| 存什么 | `{ at }` |
| 出现在 | 人物页卡片角标、书架「收藏」、「全部篇章」行 |
| 取消 | 同一处再按一次；书架上也能取消 |

- **一键、就地、不确认。** 取消的后果是「从书架消失」，重新收一次两次点击——比确认弹窗便宜。不做撤销 toast（项目没有全局提示系统）。
- **状态可见**：`aria-pressed` + 实心／空心两态 + `title` 带篇名（「收藏〈赤壁〉」）。不能只靠颜色——朱色与赭色在本项目的对比度检查里是分开验的（`verify.mjs:250-345`）。
- **不用 `★` 字形**（§1.2 末）。用「收」字或朱点印章的语汇，与「从头读」同一套动词。
- **星标不改变篇序。** 不置顶、不重排——篇序是内容结构，收藏一下不等于要重排这本「书」。

### 3.3 朱批（右侧面板的第六个页签）

#### 页签

`TABS`（`StoryClient.jsx:56-62`）加一项：

```js
{ k: 'notes', label: '批注' }
```

放在最后，不插在中间——已有五签是读者熟悉的顺序，新东西不挤占老位置。

#### 入口（从正文）

每段末尾的操作行现在是 `[◆ · 依据 012]`（`StoryClient.jsx:881-891`），右边加同字号的「批注」：

```
  ◆ · 依据 012          批注
```

- 没有批注：安静的次要文字（`--mo-mute`）。
- 有批注：变朱色。**这是「哪里写过」的唯一线索**——正文里不出现任何批注文字。
- 点一下：打开面板 → 切到「批注」→ 定位到这一段（复用点「依据」的 `showPanel`）。
- 面板已经开着时，直接点页签即可。

#### 页签里是什么（跟着当前段）

- 上半：**这一段**的批注。有就朱色楷体一句 ＋ `[改]` `[删]`；没有就 `这一段还没有批注` ＋ `[写一句]`。
- 下半：**本篇其余批注**，一行一条（`第 5 段 · 那句批注开头的十几个字`），点它就滚到那一段并切过去（复用已有的 `scrollToBeat`，`StoryClient.jsx:367-370`）。
- 这样既写得了当前段，也能一眼看到这篇自己批过哪些地方——不用跑回书架。

#### 写（尽量少步骤）

1. 点「写一句」／「改」→ 面板内出现输入区，自动聚焦，光标在末尾；
2. 保存：`Cmd/Ctrl+Enter`、失焦、或「存」；`Esc` 取消；
3. 中文输入法 `compositionstart/end` 期间不保存；
4. 上限 120 字；
5. 清空保存 = 删除（另有一个「删」做显式删除）。

#### 跟随与锁定

- 页签跟着当前段走（与「依据」一致）。
- **编辑期间锁定当前段**，滚正文不切换：显示「正在写第 5 段」，保存或取消后恢复跟随。复用面板已有的「主动查阅暂停跟随」机制（`docs/书页旁批落地与滚动联动回归-2026-10-19.md`）。
- 收起面板：失焦即存，不丢。

#### 内容改版

批注存 `{ text, at, anchor, moved }`，anchor = 该段首 16 字。段数变了用 anchor 重定位；找不到就**保留批注并标「这一段已改动」**，不静默丢。

#### 手机

手机没有常驻右列，批注页复用现有的段后查证容器——点「批注」时面板插在**这一段之后**（既有行为），批注在面板里，不额外占正文。

### 3.4 书架页 `/shelf`

- 路由 `app/shelf/page.jsx`。服务端给 129 篇的轻量索引（人物、篇名、段数、朝代），本机数据在客户端合并（§5.6）。
- 导航加一项：`总览 / 书架 / 设置`（`Nav.jsx:7-9` 的注释说的就是「导航只放全局入口」）。
- 行内信息：篇名 · 人物 · 进度 · 星标 · 朱批数。**不显示阅读时长、不显示百分比。**
- 130 行的「全部篇章」在手机上很长：分组标题吸顶，组间留白，不做虚拟滚动（先实测滚动性能再决定）。

### 3.5 数据可携带（导出 / 导入）

- 设置页拆三块：**阅读进度**（导出／清除）、**收藏与朱批**（导出／清除）、**场景区浅色**（不变）。
- 导出：`.json` 文件 ＋ 可复制文本（iOS 上文件下载不一定好用）。
  ```json
  { "app": "guanshi", "schema": 2, "exportedAt": 1762…,
    "progress": { … }, "library": { … } }
  ```
- 导入是**合并不是替换**：同键取 `at` 较新者；导入前给预览（「将带来 12 篇收藏、34 条朱批，其中 3 条本机已有」），不让读者盲点。
- 清除加一次确认。现有文案（`SettingsClient.jsx:23`）只提进度与复习，必须改，否则读者会以为收藏一起没了。

## 4. 数据设计

### 4.1 三个键，三种职责

| 键 | 内容 | 生命周期 | 清除入口 |
|---|---|---|---|
| `guanshi.settings.v2` | 明暗 | 随时可丢 | 不需要清 |
| `guanshi.progress.v2` | 读到第几段、复习标记 | **可丢**（最坏是重读） | 设置页「清除阅读进度」 |
| `guanshi.library.v1` | 收藏（stars）、朱批（notes） | **不可丢**（读者亲手留的） | 设置页「清除收藏与朱批」，独立确认 |

**为什么收藏与进度必须分开键**：`clearProgress()` 现在 `removeItem` 整个键（`progress.js:105-109`）。收藏放进去，设置页那个按钮就从「清进度」变成「删掉读者攒了三个月的东西」，而按钮上写的还是「阅读进度与复习状态」。

**为什么收藏与朱批同一个键**：它们都是「读者亲手留下的」，一起导出、一起清除、一起确认。分成两个键只会让「清除」和「导出」各多一套。分开的边界在**键这一层**（进度 vs 读者创作），不在集合这一层。

### 4.2 `progress` v2

```js
{
  v: 2,
  read: {
    "caocao/09-chibi": {
      beat: 6,                    // 读到第几段
      beats: 9,                   // 存的时候共几段（判断内容改没改）
      anchor: "九月，曹操到了新野",  // 段首 16 字，改版后重新定位
      done: false,                // 派生值，判定以 beat >= beats 为准
      doneAt: null,
      phase: "live",
      at: 1762…
    }
  },
  review: { "caocao/09-chibi": { "3": "known" } },
  at: 1762…
}
```

**键名不改，版本放在载荷里**（`guanshi.progress.v1` 里存 `v: 2`）。

原来打算换键名 `...v2`，实现时改了主意的两个理由：

1. **旧版仍能读**：旧代码只认 `read` / `review` 两个字段，不认 `v`。同一键写 v2 载荷之后，
   `git revert` 回去的旧版照样读得到——换键名反而做不到这一点（旧版看不见新键）。
2. **测试夹具不用一次性搬迁**：`guanshi.progress.v1` 在 7 个脚本里出现 38 次。
   同键 + 载荷版本让这些夹具原样成立（它们写的载荷没有 `v`，走 v1 → v2 迁移）。
   换键名要改 38 处，每处都可能改错，而迁移逻辑的验证并不依赖换键。

代价是键名与载荷版本不一致——写在 `lib/progress.js` 的注释里，别让它成为下一个人的坑。

**`last` 删掉**：全仓无读者，留着只会继续制造跨人物误清。

### 4.3 `library` v1

```js
{
  v: 1,
  stars: {
    "caocao/09-chibi": { at: 1762… }              // 收藏：键=人物/篇
  },
  notes: {
    "caocao/09-chibi": {
      "5": { text: "…", at: 1762…, anchor: "曹操进军江陵", moved: false }
      // 键=段号；anchor 用于内容改版后重定位；moved 表示段已改动、位置可能不准
    }
  }
  // 将来若做摘录：passages: { "caocao/09-chibi#042": { at, excerpt, origin } }
  // 现在不写这个空字段——空对象会让「这个集合存在吗」变得含糊
}
```

- **摘录留位不实现**：加进来时 `stars` / `notes` 一个字不用改。
- **不存篇名**：篇名从内容索引取（书架服务端给 129 条轻量索引）。存了会陈旧。
- **朱批必须带 anchor**：本书的正文一直在改（`content/` 里 130 篇几乎每轮都有修订），只存段号等于把读者的话绑在一个会动的编号上。

### 4.4 键的规范（一条铁律）

**所有键一律 `人物/篇`，不允许只用篇 id。**

`01-jingkou` 同时属于 `liuyu` 与 `tandaoji`（实测 129 个唯一 id 里有 1 个重名）。今天只有 `progress.js:100` 踩这条，明天书架分组、导出合并都会踩。写进 `lib/` 注释，并用单测钉死（§5.7）。

### 4.5 容量（估算，不是实测）

| 项 | 单条 | 上限 | 占用 |
|---|---|---|---|
| 进度 | ~150B | 130 篇 | ~20KB |
| 复习标记 | ~30B/卡 | 约 1400 张 | ~40KB |
| 收藏 | ~60B | 130 篇 | ~8KB |
| 朱批 | ~250B | 130 篇 × 平均 3 条 | ~100KB |

**总计约 170KB，5MB 配额用不掉 4%。** 所以不需要条数上限、不需要截断策略、不需要 LRU。**但写入失败仍然不能静默**：现在 `persist()` 是 `catch {}`（`progress.js:43-49`）——读者攒的东西不能悄悄消失。

## 5. 工程设计

### 5.1 抽一层 store 基座

现在两份复制（`progress.js`、`settings.js`），加 library 就是三份。三份的读盘逻辑**已经分叉**：`settings.js:26-33` 用 `{...DEFAULTS, ...parsed}`，`progress.js:28-41` 逐字段校验。这不是风格差异，是两套错误容忍策略。

**`web/lib/store.js`**，导出 `createPersistentStore({ key, version, defaults, migrate })`：

```js
{ get(), subscribe(fn), write(updater, { silent }), reset(), exportJSON(), importJSON(json), status }
```

负责：读盘容错、版本迁移、写入合并、跨标签页同步、写失败降级、订阅广播。
`progress.js` / `library.js` / `settings.js` 变成三份二三十行的定义。

**顺序**：先建基座，**新代码（library）直接用它**；`progress` 的 store 化放在阶段 1（那时已有 `verify:progress` 当回归网，且阶段 0 已修掉已知 bug）。

### 5.2 订阅：`useSyncExternalStore` + selector

现在 `useState(state)` + 每次 `markRead` 都 `emit`。后果是每推进一段，**所有订阅者都重渲染**：`StoryClient`（979 行）、`ReviewCards`、`RecentRead`，加了书架后还有整个书架。

```js
const read = useStoreSelector(progressStore, s => s.read[storyKey(person, story)])
```

- 选择器返回稳定引用，无关更新不触发渲染；
- `getServerSnapshot` 直接给空态，替掉现在 `ready` 标志的两段式渲染（`progress.js:113-121`）；
- 写入侧留 `{ silent: true }`，高频推进不广播给书架。

**诚实说明**：这不是为了「变快」——806 个情节点、10 段一篇，重渲染量很小。理由是**一个状态只有一个真相**：现在 `progress.js:25` 的模块级 `state` 由「谁最后调 `loadProgress()`」决定，两个订阅者挂载顺序不同会读到不同快照。同款事故在 `settings.js:5-13` 的注释里已经记过一次。

### 5.3 锚点：进度与朱批共用一套

```
if (saved.beats === beats.length)  → 用 saved.beat
else → 用 anchor 在当前 beats 里找「段首包含该串」的段
       命中 → 用该段
       未命中 → clamp(beat, 1, beats.length)，标「已调整」，并在入口告知
```

这替代 `OPENING_EDITS`（`progress.js:57-61`）。原来那三篇的改动是「把前情搬走」，**读者所在那段的文字没变**，锚点必定命中。
真正命中不了（那段被重写）时，clamp 是唯一不撒谎的选择——所以必须**告知**。

朱批用同一套：批注的 anchor 找不到时，**保留批注并标 `moved`**，段号就近，不删。

### 5.4 卡片结构：星标按钮不能嵌进 `<Link>`

人物页整张卡是一个 `<Link>`（`app/p/[person]/page.jsx:105-112`）。在 `<a>` 里放 `<button>` 是非法嵌套：键盘 Tab 会跳过或聚焦异常，读屏会读出两个角色。

```jsx
<div className="story-card ready">
  <Link className="sc-hit" href={…} aria-label={`进入〈${s.name}〉`}>…</Link>
  <button className="sc-star" aria-pressed={…}>收</button>
</div>
```

- `Link` 当覆盖层（`position:absolute; inset:0`），星标 `z-index` 更高；
- 卡片右侧已有 `padding-right: 90px`（`globals.css:975-977`），星标正好落在印章预留位，**不重排现有布局**；
- 390px 下不能压到标题——要实看，不能只看桌面。

### 5.5 批注在面板里：复用现有机制，别新造一套

这一块的风险不在「写」，在**面板**。批注页必须借用面板已经解决过的机制，不要另写：

| 已有的机制 | 批注怎么用 |
|---|---|
| `showPanel(trigger)`：记触发点、挂载位置、返回锚点 | 「批注」按钮直接调它，再 `setTab('notes')` |
| 跟随当前段（`following` / `shownBeat`） | 批注页显示当前那一段的批注 |
| 主动查阅时暂停跟随（原文／背景／映射／人物已用过） | 编辑期间同样暂停，锁定段号，显示「正在写第 5 段」 |
| `Esc` 与焦点返回 | 编辑中 `Esc` 先退出编辑、不关面板；再按一次才关 |
| 手机段后挂载（`data-panel-host`） | 批注页跟着同一套挂载，不新增容器 |

**新增的、必须实测的三件事：**

1. **六页签在 390 / 320 的排版。** 现在五签已排满一行（`.panel-tabs`），第六签会溢出或折行；要做紧凑间距或横向滚动，且不能把「收起」挤出屏幕。
2. **编辑中的跟随锁定。** 滚正文时面板会换段（既有行为），编辑态必须挡住它；实现要复用已有的「暂停跟随」标志，不要新加一个状态。
3. **手机键盘弹起时，面板内的输入是否稳定。** 这条**没验过**，必须在 390 实测。

**注意**：这个方案会碰面板代码，所以 `npm run verify:panel`（28 篇 203 段、406 次开关、五页签）**必须全量重跑**，并补上第六签的开关。上一版写「一行都不碰那两套滚动逻辑」——现在不成立了，风险按实算。

### 5.6 书架的数据来源

书架是静态页（`generateStaticParams` 只覆盖人物/故事页；书架本身没有动态段）。
服务端从 `data/content.json` 取 129 篇的轻量索引（人物 id／名、朝代、篇 id／名、段数），约二十 KB；进度、收藏、朱批全部在客户端读本机。

**切换视图不写 URL**：写 `?view=all` 就需要服务端读 query，会让页面转成动态渲染。用 `useState`，默认「我的」。

### 5.7 测试策略（每项都必须能失败）

**单测（`node --test`，与 `test:cards`/`test:sources` 同一套跑法）**

| 用例 | 断言 |
|---|---|
| v1 → v2 迁移 | 造 v1 夹具，读出的 `read/review` 与原值逐字段相等；v1 键仍在 |
| 坏数据 | `null`/`[]`/`{"read":"x"}`/截断 JSON → 空态，不抛 |
| 锚点重定位（进度） | 段数 9 → 6、当前段文字仍在 → 落在同一段的文字上 |
| 锚点重定位（朱批） | 段数变化后批注仍挂在同一段文字上；找不到则 `moved=true` 且不删 |
| 跨人物同名篇 | `reset liuyu/01-jingkou` 后 `tandaoji/01-jingkou` 原样不动 |
| 合并写入 | 磁盘有 A、内存写 B → 两者都在 |
| 朱批边界 | 空串保存 = 删除；120 字上限；纯空格不算内容 |
| 导入合并 | 同键 `at` 较新者胜；预览条数与落盘一致 |

**浏览器验证（新增 `npm run verify:library`，照 `verify-reading-progress.mjs` 的隔离 context，不碰真实用户数据）**

1. 星标一键 → 刷新仍在 → 书架「收藏」出现 → 点回该篇；
2. 批注：点「批注」→ 面板切到「批注」页 → 写 → 保存 → 刷新 → 页签里仍在 → 书架行出现「朱批 1」；
3. **清除阅读进度后，收藏与朱批仍在**（§4.1 的验收）；
4. 导出 → 清空 → 导入 → 条数与内容一致；
5. 坏数据注入 → 无控制台报错、能正常读；
6. 书架两视图：默认「我的」、切「全部篇章」、130 行不横向溢出、分组标题吸顶；
7. 390 / 1440：六页签不溢出、批注页不遮正文、编辑时滚正文不换段、触控目标 ≥44；
8. **负向**：故意把「失焦保存」改坏，确认第 2 条会红。

**回归**：`verify:progress`（改造夹具后）仍绿；`npm run verify` 全量；**`npm run verify:panel` 全量**（28 篇 203 段、406 次开关，另补第六签的开合）；`npm run check`（新文案要过 `check-ui-words` 三类闸门：待办、改稿史、内部行话——「localStorage」「schema」「迁移」不能出现在读者可见的字里）。

**夹具迁移**：`guanshi.progress.v1` 在 7 个脚本里出现 38 次。在 `scripts/fixtures.mjs` 提供 `seedProgress(page, obj)` 一次性替换。
**不要**为了少改测试而继续用 v1 键名——那样迁移逻辑永远测不到，而迁移正是最容易丢数据的环节。

### 5.8 失败模式清单（实现时逐条对照）

| 失败 | 现在 | 应该 |
|---|---|---|
| localStorage 不可用 | 静默失败 | 按钮置灰 + 「这台设备没有可用的本机存储，收藏不会保存」 |
| 配额满 | 静默（`progress.js:43-49`） | `status='degraded'`，可见提示 + 引导导出 |
| JSON 损坏 | 当空（`progress.js:38-40`）✅ | 保持；不顺势覆盖原值（留证据） |
| 两标签页同时改 | 后写者整对象覆盖 | 监听 `storage` 重读；写前「读—合并—写」 |
| 内容改版 | 硬编码，可能静默跳段 | 锚点重定位 + 未命中时明确告知 |
| 朱批所在段被重写 | —（不存在） | 保留批注，标「这一段已改动」 |
| 收藏的篇被删 | — | 条目保留并标注，可手动移除 |
| `01-jingkou` 重名 | `resetStory` 误清 `last` | 键一律带人物（§4.4） |

### 5.9 不引入新依赖

`store.js` 手写约 120 行；`useSyncExternalStore` 是 React 内置（本项目 React 19）。
不引 `zustand`/`jotai`/`localforage`：依赖表只有 5 个包，「纯 CSS、无 Tailwind」的取舍写过理由（`web/README.md:204-211`）——保真与可控优先。

## 8. 两处判断错在哪（留着）

### 8.1 第一处：把收藏当成点赞

上一版 §2.2 把收藏判成「点赞」，据此写下三条错误推理：

1. 「星标必须保持一键，否则会变成填表单」——**把转化漏斗套在一个只有一个读者的工具上**。此人按下的每一次都是有意为之，这里没有比例要优化。
2. 「短注会引入编辑态、失焦保存、移动端键盘，不改变能不能收藏这一核心价值」——**反了**。按存目模型，一句「为什么留」正是收藏能活过一年的原因；把理由留到书架上补，理由已经没了。
3. 「书架偏薄，补一行进度总览当填充」——那是用别的功能给一个想错的功能凑内容。

### 8.2 第二处：把朱批放在段后

同一版又把朱批设计成段后夹批，理由是「不碰面板那两套滚动逻辑，风险最低」。用户当场指出两个错：

1. **批注一多，正文就被自己的话切碎。** 读者来读史，结果一直在读自己的注解——这和「正文是书页」直接冲突。
2. **「页签会让人分不清哪句是史料」这个担心不成立。** 独立页签本身就是分隔；点进去全是自己写的，不点就看不见。我把它想成了「混进正文的某种样式」，那是想错了对象。

更该被指出的是：**本项目已经做过一次一模一样的判断。** 人物介绍原本是段后卡，被否定后放进既有「人物」页签（`design/character-notes-2026-10-24/人物笺设计.md` 开头即写「此前把人物介绍接在正文下方的方案已否定」）。那份文档我在同一轮里读过，仍然又设计了一遍段后卡。

**两处的共同点**：不是没做研究，是**研究完仍然用自己脑子里的默认形态覆盖了已经成立的结论**。8.1 是产品惯性（点赞），8.2 是工程惯性（少碰复杂代码）。后者更值得记：**「低风险」是一个关于改动范围的判断，不是关于用户收益的判断**，拿它当设计理由，就会把成本省在读者身上。

## 10. 实施追记（边做边改，写在这里免得和规划混在一起）

### 10.1 已经定下来的实现选择（与上面正文不同的地方，以这里为准）

| 项 | 规划里写的 | 实际做法 | 为什么 |
|---|---|---|---|
| 进度的键 | 换键名 `guanshi.progress.v2`，旧键只读 | **键名不动，版本在载荷里**（`v:2`） | 旧版仍能读（回滚安全）；38 处测试夹具不必搬迁 |
| 首页分组 | 未涉及 | `groupByEra` 先做繁体→简体再匹配 | 11-01 新增五人时代串是繁体，否则各自占一个「朝代」 |
| 首页检查 | 未涉及 | 从内容库推导人数 + 针对性断言，不再写死 14 人 | 写死人数只会训练出「改测试让它绿」 |
| 收藏导出 | 规划里在「数据可携带」一节 | 备份文件里每样数据带**自己的** schema | 旧备份才会走 migrate；顶层 schema 只表示文件格式 |
| 收藏的键 | `guanshi.library.v1`，`stars` 平表 | 同 | — |

### 10.2 实施中抓出来的真 bug（都不是审出来的，是跑出来的或审出来的）

1. **`ready` 恒真**：`useProgress` 一开始返回 `ready: true`，恢复逻辑在「服务端默认值」那一帧就跑了，
   `restoredRef` 被锁死，刷新后不续读。改回挂载后再置位。
2. **先 clamp 再减段**：旧改动表在 `resolveResume` 里顺序反了，7 段减 5 被夹成 1（应为 2）。
3. **合并顺序把删除复活**：`persist()` 里「读—合并—写」会把读者刚取消的收藏合并回来。
   改成「先拉取、再应用本机改动」；写失败（degraded）期间干脆不拉。
4. **CSS 特异度 blocker**：`.story-card > *:not(.seal)`（0,2,0）把 `.sc-star`（0,1,0）的 absolute 压回
   普通流——按钮掉到卡片左下、每张卡高 44px。而我那条「收藏不压字」的临时检查**因此是假绿**。
   已经写成永久检查（position/位置/三方不相交/触控尺寸/整卡可点）。

### 10.2b 第二轮实施又抓出两条（书架与朱批那一轮）

5. **批注被锚点挪过之后，按显示段号再写会变成两条**：`#3` 那条显示在第 6 段，
   编辑时若按第 6 段写，就生成 `#6` 而 `#3` 还在。改成 `notesFor` 返回原键、按原键更新。
6. **滚到页底却不算读完**：矮篇 + 高屏时，末段顶部到不了 140 的阅读线，
   读者把页面滚到底，进度仍停在第 n-1 段。现在「自己向下滚到页底」算读到末段；
   「恢复位置本来就在页底」不算（用进入时的滚动位置区分），
   否则刷新到第 6 段会被误判成读完。

### 10.3 两次「探针错了，不是产品错了」

- 锚点用例在生产构建上报「没滚到第 6 段」：真实原因是探针只等了两帧，恢复滚动要等布局稳定。
- 收藏用例报「aria-pressed 没变」：真实原因是按钮名字随状态翻转，按名字取到的已是下一张卡。

教训：**先怀疑探针，再怀疑产品**；但也不能反过来把真 bug 当探针问题——第 3 条就是真 bug。
