# 观史 · 项目整体评估

评估日期：2026-10-17（北京时间）。代码基线：`cf22520`。

**后续范围确认：用户已明确不需要 AI 对话功能。研发执行以《问题清单与研发整改任务书-2026-10-17.md》为准；删除 AI 功能规划及现有误导入口，保留静态预置问答资料。**

## 评估范围与结论

本次检查了项目设计文档、内容规范、审校记录、开发计划、前端路由与组件、内容编译与维护脚本、设计系统和参考文本配置；逐篇阅读了十八篇故事的运行时正文，抽查问答、背景卡、复习卡与直译，并对重点历史问题进行了原始文献对读。实际检查了运行中的本地站点，包括桌面与手机尺寸、明暗模式。

这是项目整体评估，不是对全部 1,287 条问答、177 张复习卡和 325 段直译逐条完成的新一轮人工审校。下文明确区分已复现的故障、内容中可直接定位的问题和架构建议。

**判断：项目已经建立了有辨识度的历史阅读产品，以及服务它的内容生产系统。当前最需要补强的是从史料到叙事、从 Markdown 到页面、从阅读到记忆这三条链路的完整性。**

现阶段适合继续使用 Markdown、构建期编译和静态页面。没有出现必须引入数据库、复杂后端或实时 AI 才能解决的问题。

## 一、项目实际是什么

当前架构可以概括为：

```text
公版参考文本 .refs/ ──────────────→ check-sources（文字一致性）
          ↑                                  ↑
       refs.json                        source.md
                                             ↓
人物 / 篇目 / 故事 / 问答 / 复习 / 直译 Markdown
                     ↓
         build-content.mjs（解析、编译、校验）
                     ↓
              web/data/content.json
                     ↓
        Next.js 服务端页面 → 客户端阅读交互
                     ↓
           verify.mjs（浏览器抽查与遍历）
```

阅读层级是总览 → 人物 → 故事；每个人物还有完整资料页。故事页提供入场铺陈、逐段推进、依据、原文、背景、映射、在场人物、复习和预置问答。

| 项目 | 曹操 | 荆轲 | 合计 |
|---|---:|---:|---:|
| 已实现故事 | 10 | 8 | 18 |
| 故事内部段落 | 95 | 66 | 161 |
| 底本段落 | 232 | 93 | 325 |
| 直译段落 | 232 | 93 | 325 |
| 预置问答 | 807 | 480 | 1,287 |
| 复习卡 | 113 | 64 | 177 |
| 背景卡 | 78 | 48 | 126 |
| 正文原文块 | 32 | 14 | 46 |

这些数字来自当前编译产物，并与本次内容检查输出核对。曹操故事声明范围覆盖 78/232 段，荆轲覆盖 93/93 段；曹操其余 154 段主要通过完整资料页访问。这里统计的是声明范围覆盖，不等于每段都已经被叙事充分使用。

实际产品目前以阅读为主。提问入口放在读完后的复习卡之后；没有实时 AI 调用，也没有持久化的阅读进度、掌握状态或复习调度。早期设计中的“随时打断人物提问”和当前阅读顺序之间，需要在现行产品说明中明确取舍。

## 二、值得保留的基础

### 架构

1. **内容源与运行产物分开。** Markdown 方便作者审校，JSON 方便程序消费；内容变更有 Git 记录。
2. **人物和故事由数据驱动。** 动态路由、人物目录、前后篇导航已经支持第二个人物，不再只围绕易水送别组织代码。
3. **把重复故障变成了校验。** 引文编号、小说标记、篇名与范围对账、重复正文、占位内容等都有针对性检查。
4. **客户端数据已经收窄。** 故事页没有继续把其他九篇故事和全人物底本一并传给浏览器。
5. **工具链保持克制。** 当前内容规模和交互复杂度适合现有实现，无需为了扩展预先搭建大型服务。

### 设计

暗场叙事与纸面查证之间的差异有明确用途；宋、楷、黑体承担不同语义；纸纹和朱批印也与阅读行为相连。实看桌面故事页，这套视觉语言成立，值得延续。

用户能在故事中读到白话，再追到对应原文；原文中的关键台词保留力度；复习卡先显示问题、主动展开答案。这些决定都服务于学习，而不是单纯增加装饰。

### 历史内容

项目已经主动区分原文、推演、争议、未载、小说和产品说明，也承认电子本比对的能力边界。官渡兵力争议、吕伯奢三说等材料已经进入内容，说明项目具备开展史料辨析的基础。

## 三、已经复现的工程与体验问题

### 1. 完整资料页的桌面排版损坏，优先修复

位置：`web/app/globals.css:983`、`web/app/p/[person]/source/page.jsx:87`。

每条资料使用 `64px 1fr` 两列，但三个子元素依次是编号、原文、直译。直译没有指定列，自动落入第二行第一列。1440 像素宽度实测，曹操第一段直译宽 **64px**、高约 **353px**，整条资料高约 **414px**。

同时，原文颜色读取 `--ink`，而这个变量实际用于朱红墨痕，所以原文大段呈红色。字体变量也写成了 `--song`，与设计系统的 `--f-song` 不一致。

建议：编号单列；原文与直译共用正文列；文字使用明确的正文色与字体变量。对两个完整资料页分别检查桌面、手机、明暗模式和长段文本。

### 2. 背景卡中的表格被静默丢弃

位置：`web/scripts/build-content.mjs:655`；实例：`content/people/caocao/stories/09-chibi.md:182`。

“谁烧的船”背景卡在 Markdown 中有三行出处对照表。解析器只收普通段落，跳过所有以 `|` 开头的行，产物中没有表格。页面保留了“还有两说”和“三本书，三个方向”，却没有中间的具体对照。

这是内容保真故障。建议为背景卡使用显式段落、表格等内容块；如果暂不支持表格，应在编译时拒绝该结构，而不是吞掉它。复习卡已经支持块结构，可沿用思路。

### 3. 部分文案校验没有扫描到它声称覆盖的字段

位置：`web/scripts/build-content.mjs:2235`。

末尾“读者看得见的地方”扫描使用了 `st.blocks`、`sd.ground`、`cd.a` 等字段，但实际内容分别在 `st.backgrounds`、`sd.meta`、`cd.blocks` 中；人物“引子”也没有正确接入这段扫描。前面另一套检查覆盖了一部分内容，但两套规则和字段列表已经分叉。

在临时隔离副本中，向赤壁背景卡加入“本文件早先写成另一版本，需另行核对。”，`build-content.mjs --check` 仍然退出 0，仍报告 33,773 项通过。

建议所有面向读者的文字共用一个明确的遍历入口，让校验规则消费同一组字段；为每条重要规则保留一个应当失败的样例。检查项数量不能代替覆盖证明。

### 4. 首页同时出现两张曹操卡片

位置：`web/lib/content.js:63`、`web/app/page.jsx:11`。

曹操已经是已实现人物，但仍在 `PLANNED` 中。页面同时显示可进入的曹操和锁定的曹操。实际页面已经复现。

建议计划与已实现人物共用稳定 ID，在数据合并时去重。时代排列也应使用明确的时间顺序，当前按人物目录顺序插入会先出现三国，再出现战国末。

### 5. 设置状态各自维护，出现界面不同步

位置：`web/lib/settings.js:29`。

导航和设置页各调用一次 `useSettings()`，各持一份独立状态。设置页开启浅色后，页面变浅，但导航仍显示“暗场”，已在浏览器复现。

AI 开关也允许显示“已开启”，文案承诺可以自己输入问题，而当前没有能力探测或自由输入实现。

建议用一个共享设置状态。根据用户后续确认，移除 AI 开关和自由对话承诺，不补建能力探测或对话服务。

### 6. 依据引用还没有形成完整的可操作路径

本次检查有 **10 篇故事的跨范围引用提醒**。这些不是十条引用：每篇可能包含多处，其中易水送别有 48 处。

编号通常被渲染成普通文本或 `<code>`，不能直接跳转。完整资料页虽然已经有 `#s-编号` 锚点，读者仍需要退出问答、找到另一页、再手动找编号。

建议让引用成为结构化链接：当前篇可展开，跨篇可跳到完整资料的精确段落，并可返回原来的阅读位置。合法的跨篇引用可以保留，但不应留下查不到的指针。

### 7. 浏览器验证遗漏完整资料页

位置：`web/scripts/verify.mjs:48`。

现有路由清单是首页、设置、两个人物页和十八个故事页，共 22 条；两个完整资料页没有加入。因此本次全部十三项通过，与完整资料页仍存在明显故障并不矛盾。

浅色扫描使用的 2.8:1 是脚本明确命名的“灾难性地板”，不能当作完整的无障碍合格证明。[WCAG 1.4.3](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum) 对普通文字通常要求 4.5:1，大字要求 3:1。

另外，提问浮层没有对话框语义、焦点圈定和关闭后的焦点恢复；仅处理了 Escape。应补一条完整的键盘操作检查。

## 四、历史学评估：出处之外，还需要解释的纪律

### 1. “旁若无人”被译成了“旁边没有人”

位置：`content/people/jingke/stories/01-yanwei.md:111`。

底本写的是在市中歌哭、旁若无人，表达不顾旁人。正文却明确说“旁边没有人”；同一文件的说明又正确解释为“不在乎”。人物简介则加了“街上的人都看着他们”，这也不是该句直接提供的信息。

这说明原文逐字核对可以全绿，白话仍然改变事实。应统一为“不顾旁人的眼光”一类译法，并检查简介、故事、种子、复习卡有没有同一错误的不同版本。

### 2. “没有记载说话”被回答成了“什么都没说”

位置：`content/people/jingke/cards/06-yishui.md`，卡 3。

问题问太子丹在易水说了什么，答案第一句是“什么都没说”，后面才说史书没有记录。两者不是同一判断。读者最容易记住的恰恰是答案首句。

卡 1 对白衣冠先确定地回答“送葬的装束”“都认定他不会活着回来”，同时又标存疑。这种写法把不确定性留在小字里，把结论写在大字里。

建议让答案主句本身承担证据边界，例如“这段记载没有留下他的话”“常被解释为送死之服，但原文没有说明”。标记辅助措辞，不能替措辞负责。

### 3. 官渡的兵力争议需要进入主叙事措辞

正文说曹操兵不满万，标 ◆；背景卡另以 △ 介绍裴松之的反驳。项目并未漏收争议，但主叙事的确定语气与背景的存疑提示分离了。

《武帝纪》确有这个数字，裴松之也在紧接的注中提出系统质疑。可采用“《武帝纪》把他此时的兵力记作不足一万”这类有归属的表达；如果不希望正文谈书，则让该处的依据入口直接提示争议。[原始文献对读](https://zh.wikisource.org/wiki/三國志/卷01)。

### 4. 赤壁的史料比较缺了一块关键材料

现有材料把黄盖火攻主要放在演义一栏，再与刘备烧船、曹操自烧船并列，容易使读者误以为黄盖火攻只有小说来源。

《三国志·周瑜传》正文已经记载黄盖建议并实施火攻；《吴主传》另记曹操烧掉余船后退。因此，敌方火攻与退兵时焚毁余船也未必是相互排斥的两个版本。必须先辨明时间、对象和行为，再判断是不是冲突。[《周瑜传》](https://zh.wikisource.org/wiki/三國志/卷54)、[《吴主传》](https://zh.wikisource.org/wiki/三國志/卷47)。

现有背景、种子、卡片和映射表还把曹操信中“孤烧船自退”一句标到《吴主传》。本次对读定位到《周瑜传》裴注引《江表传》。应核改具体出处，而不是只保留“某本吴书”这样的近似归属。

### 5. 人物判断写得有力量，但有时越过了证据

荆轲引子强调“不是刺客，是去签一份合同”，又把任务失败归结为“他还想签成”。这能改变常见阅读角度，但底本给出的方案包含劫持与刺杀，临死自述也不等于已经证实的唯一失败原因。

建议保留“劫持优先”的重要观察，把“合同”明确作为现代比喻，并将失败原因表述为荆轲自己的解释。历史人物的自述、史家的评语和作者的解释应当分别可辨。

### 6. 当前底本边界适合阅读一篇传记，还不足以承担人物全貌

以《武帝纪》组织曹操，能够形成统一阅读线索，但主角纪传天然限制了其他人物和事件的可见性。曹操的十篇又以仕途、军政转折为主；徐州战争、张绣之战、献帝与皇后等问题尚未成为故事，读者得到的人物形象会受选题影响。

扩篇时应先编制人物的关键问题与相反证据清单，再决定收哪些传记与故事。对战事尤其需要对方人物传记、制度材料和地理线索的适量对读。新增史料不必全部进入正文，可以进入有明确出处的背景与辨析。

## 五、三种专业视角共同指向的结构改进

### 1. 分开记录“出处是什么”和“这句话有多确定”

目前“正史 / 注 / 小说 / 野史”是来源分类，◆○△等又承担主张可信度和语言形式的解释，几种维度挤在一起。

尤其“注”既包含转引古书，也包含注者自己的判断；当前 `243` 的出处甚至写成“裴松之注引臣松之”。同一部非官修记载，经裴注转引时与单独收录时，也不应仅因载体不同就改变它的证据性质。

建议在现有 Markdown 编译流程中逐步补足以下信息，不要求立即整体改写格式：

- 文献：书名、作者、时代、版本、文本类型。
- 段落：稳定 ID、卷篇定位、正文、转引关系、版本差异。
- 主张：陈述内容、支持或反对的段落、确定程度、适用范围。
- 叙事块：白话、原文、译文、表格等显式类型，关联到具体主张与出处。

页面上的六个标记可以继续简洁，但底层不宜只用一个字符承载全部判断。

### 2. 保留 Markdown，降低格式猜测

编译器约 2,449 行，包含解析、数据拼装、语义检查、文案检查和账本写入。它已经积累了很多有效经验，但对标题、表格、引号、特殊字形的猜测越多，静默丢失的风险越高。

建议先拆清解析、内容模型、规则、产物写入四个职责，统一读者可见字段遍历，再为高风险结构增加显式块类型。引文、白话和回译不宜长期靠“整行有引号且碰巧能在底本里找到”来推断。

范围语法与出处规则已经有共享模块，这是正确方向；完整资料页又手写了一份范围解析，应回到同一个 `parseRange`。史料 ID 与显示顺序也应逐步分离，避免扩充材料就牵动大量编号。

### 3. 把内容检查、页面检查和史学审校当成三种验收

内容检查验证结构与引用；页面检查验证实际呈现；史学审校验证白话、归属、因果和争议。三者各有用途。

优先增加少量能证明关键规则确实会失败的样例，包括：背景表格丢失、审校批注漏拦、未载变成没有发生、同一句在故事与卡片中的证据地位不一致。无需用大量镜像实现的测试来增加数量。

参考文本下载配置也宜记录版本时间、固定修订和校验值；目前 GitHub 使用移动的 `master` 地址，重新下载不保证永久得到同一份文本。继续承认公版电子本的边界即可，无需把项目变成全面版本校勘工程。

### 4. 明确下一阶段的学习体验

现有阅读、查证、看答案已经可用，但“走出来还记得住”还缺少可观察的结果。

可以先以本地存储保存阅读位置、读完状态与少量复习反馈，支持再次进入后接着读；复习卡围绕事件顺序、原因、人物立场和证据辨析组合，而不是固定追求每篇相同卡数。曹操行迹目前只有三条 189 年的事件，与十篇故事跨度明显不匹配，也应同步完善。

提问置于篇末已经是当前实现中的明确选择。应先验证这种顺序是否服务阅读，再决定是否恢复“随时提问”；不宜一边保留篇末入口，一边继续向用户承诺实时打断人物。

## 六、建议执行顺序

| 顺序 | 工作 | 完成的具体判据 |
|---|---|---|
| 1 | 修资料页、背景表格丢失、重复人物、设置不同步 | 读者可见问题消失，新增页面进入验证清单；不损失现有内容 |
| 2 | 修荆轲误译、未载措辞、赤壁出处和史料比较、官渡争议呈现 | 同一事实在人物页、正文、问答、卡片与依据中一致，主句本身不越过证据 |
