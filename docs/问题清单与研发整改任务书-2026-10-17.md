## 3. 必做整改项

### R01 · 完整资料页排版与设计变量错误（P1）

**位置**：`web/app/globals.css`，`web/app/p/[person]/source/page.jsx`。

**问题**：资料条目使用 `64px 1fr` 两列，第三个子元素“直译”自动落入编号列。桌面端实测第一条直译只有 64px 宽。原文字色又误用墨痕变量 `--ink`，大段呈朱红；字体使用了与设计系统不一致的 `--song`。

**修改要求**：编号单独一列；原文与直译在同一个正文列中上下排列；采用现有正文色和 `--f-song` 等正确变量。处理资料中的现存轻量格式，避免 `**` 等作者格式符号直接露出；不得用未经处理的 HTML 渲染内容。

**验收**：

- 荆轲、曹操两个资料页，桌面 1440×1000、手机 390×844、明暗模式均可读。
- 桌面原文和直译左边界一致，直译不进入编号列；长段不溢出。
- 原文采用正文色；没有裸露的 Markdown 格式符号。

### R02 · 背景卡表格被静默丢弃（P1）

**位置**：`web/scripts/build-content.mjs` 的背景卡解析；`web/components/StoryClient.jsx` 的背景渲染。

**实例**：`content/people/caocao/stories/09-chibi.md`，“谁烧的船”背景卡。

**问题**：Markdown 的出处对照表在编译后全部消失，页面只剩下“还有两说”“三个方向”等前后文。

**修改要求**：背景卡支持段落、表格等显式内容块，保留顺序、表头、各行文字和依据；与复习卡已有块结构协调，兼容现存背景卡。发现不支持的有效内容结构时，明确报出文件与位置，不得静默吞掉。

**验收**：

- 当前背景卡完整显示对照表；R05 修订史料后，对照表仍保持完整。
- 全部现有背景卡内容不减少、不乱序，不把编辑说明混入产品。
- 有一条针对实际内容丢失的回归检查：删除表格解析或渲染逻辑时检查会失败。

### R03 · 读者可见内容校验漏扫（P1）

**位置**：`web/scripts/build-content.mjs` 中可见字段收集与文案扫描。

**问题**：部分扫描使用不存在的 `st.blocks`、`sd.ground`、`cd.a` 等字段。隔离副本中向背景卡加入“本文件早先写成另一版本，需另行核对。”，检查仍通过。另有扫描使用正确字段，但规则与覆盖列表相互分叉。

**修改要求**：建立统一的读者可见字段遍历，覆盖人物简介与引子、时间线、故事铺陈与正文、依据、背景及表格、问答的回答/系统说明/元数据、复习卡题面/答案/表格/元数据。各条适用规则消费同一个遍历结果，保留规则对不同区域的合理区分；编辑备注、内部字段不渲染。

**验收**：

- 在隔离夹具中分别向背景、人物引子、问答依据、复习卡答案注入明确禁止的审校批注，均能失败并定位。
- 正常历史叙述、史料引文和合法产品说明不被误拦。
- 测试不污染原始内容；不得为了归绿删规则、缩小扫描范围或放宽阈值。

### R04 · 荆轲白话、复习答案与证据边界不一致（P1）

**位置**：`content/people/jingke/person.md`，`stories/01-yanwei.md`，`cards/06-yishui.md`，及相关问答、直译、映射。

**已定位的问题**：

1. “旁若无人”被正文写成“旁边没有人”；人物简介又添加“街上的人都看着他们”。应准确表达不顾旁人，避免另造现场事实。
2. 复习卡把“这一段未记录太子丹说话”先回答成“什么都没说”。未载不能变成没有发生。
3. 白衣冠卡片先断言“是送葬的装束”“都认定他不会活着回来”，再用小字标存疑。答案主句也必须保留解释的边界。
4. “不是刺客，是去签合同”“失败因为还想签成”将现代比喻与人物临死自述写成确定判断。应保留劫持优先、刺杀作为后备方案的事实，明确比喻与自述的性质，避免给出未经证明的唯一失败原因。

**修改要求**：逐处修正文义，同步核对简介、正文、问答、复习、直译和依据；正文保持自然、简洁，不把校改过程写给读者。

**验收**：逐项提供原句、修改后句子、所据段落及理由；主句与标记不互相抵消；不会因修正措辞而丢掉原文中的后备刺杀方案。

### R05 · 赤壁史料遗漏、出处误标与“互相矛盾”判断过度（P1）

**位置**：`content/people/caocao/` 下的赤壁故事、问答、复习卡、映射和必要的底本文献配置。

**问题**：

- 把黄盖火攻主要归在小说一栏，缺少《三国志·周瑜传》正文已有的记载，容易误导读者。
- 把敌方火攻、刘备烧船、曹操烧余船都处理成排他的三说，尚未区分时间、对象和叙述范围。
- “孤烧船自退”被标为《吴主传》；前次对读定位在《周瑜传》裴注引《江表传》，需要重新核实并纠正全套引用。

**可复核入口**：

- [《三国志》卷五十四·周瑜传及裴注](https://zh.wikisource.org/wiki/三國志/卷54)
- [《三国志》卷四十七·吴主传](https://zh.wikisource.org/wiki/三國志/卷47)
- 项目现有《武帝纪》正文、裴注和演义对应段落。

**修改要求**：先阅读实际文献，核实卷篇、正文/裴注、被引书名和前后文，再修改。“历史记载中的火攻”与“演义的具体文学场面”分别交代；证据不足时保留不确定性，不强行宣布各说相同或必然冲突。

若加入新原文，必须经现有源文件、编译和参考文本配置进入，采用可复核来源；不依记忆补引文，不只把新内容硬编码在页面或种子答案中。保持现有 ID 稳定，不进行全库重编号。

**验收**：

- 正文、背景、问答、复习和映射引用一致，能查到实际文献。
- 读者能分辨正史记载与演义细节，不会被引导为“黄盖火攻只有小说记载”。
- 新增来源具有准确定位与核对记录；未能核实的内容不写成定论。

### R06 · 官渡争议与注者判断的归属需要更清楚（P1）

**位置**：曹操官渡正文及相关背景、问答、复习；`content/people/caocao/source.md` 的出处元数据。

**问题**：“兵不满万”在主叙事中被确定陈述，裴松之的质疑藏在另一张背景卡中。另有 `243` 等注者按语被写为“裴松之注引臣松之”，把自述称谓当作被引作者。

**修改要求**：让读者在该处能立即识别这是有明确来源、且受到质疑的数字；在叙事措辞或紧邻的依据提示中表达，不要求用大段考据打断故事。纠正注者按语的出处，抽查混合转引段落是否把整段都错挂到第一本书名下。保留现有标记体系，明确 ◆ 证明有文本依据，不自动证明历史事实无争议。

**验收**：首次读到该数字就可发现争议并查到双方依据；“裴松之按语”和“裴松之转引某书”准确区分；不把争议强行裁定为某个新数字。

**问题**：多个 `useSettings()` 各持一份状态；设置页已变浅，导航仍显示暗场。AI 开关没有实际能力，却能显示“已开启”。

**验收**：任一入口切换主题后，另一入口、页面和持久化值同步；刷新和路由切换仍正确；旧设置不会导致崩溃或恢复 AI 入口；没有生成式对话的新实现。

### R09 · 引用可直接查证并返回阅读位置（P2）

**位置**：`RichText.jsx`、`StoryClient.jsx`、`SeedSheet.jsx`、`ReviewCards.jsx`、完整资料页及共享范围解析。

**问题**：跨篇编号多为文字或 `<code>`，当前原文页签不能查到范围外资料，读者要自己寻找其他页面。完整资料页也重复实现了范围解析。

**修改要求**：引用携带人物、段落等必要上下文；当前篇可定位相应依据，跨篇可打开完整资料精确锚点。核查后能回到原阅读段落或原问答，避免重新推进整篇。年份、数量和普通三位数不得误变成引用。范围解析统一使用 `web/lib/range.mjs`。

**验收**：至少覆盖当前篇引用、跨篇引用、区间引用、普通年份和不存在的引用；所有有效引用可到达，无效引用有明确检查错误。不得靠删除合法引用或随意扩大每篇原文范围消除提醒。

### R10 · 页面验证、可读性和静态问答浮层可访问性（P2）

**位置**：`web/scripts/verify.mjs`，全局 CSS，`SeedSheet.jsx`。

**修改要求**：

- 从内容数据生成全部真实页面的验证清单，覆盖完整资料页；当前页面规模至少包含原来的 22 条和两个资料页。

**验收**：390px 手机无横向溢出；1440px 桌面布局正确；键盘可打开、浏览、关闭问答并返回原入口；降低内容保真或破坏资料布局时相关检查会失败。

**位置**：`web/README.md`，`content/README.md`，`docs/项目设计文档.md`，`content/people/caocao/person.md`；其他被当前开发流程直接引用的说明。

### R12 · 本地阅读进度与复习状态（P2，明确限于最小功能）

**位置**：故事页、人物页、复习卡与必要的本地状态模块。

**问题**：当前阅读推进和答案展开主要在组件内，刷新或再次访问无法可靠接着读；复习没有个人状态。

**修改要求**：仅使用本地存储，按人物 ID 与故事 ID 保存已读到的位置、读完状态和最近阅读入口；再次进入可继续，也可主动从头阅读。复习卡可记录“待复习/已掌握”，允许修改和重置。不要把“展开过答案”自动等同于掌握，不增加登录、云同步、提醒或复杂记忆算法。

**验收**：刷新、往返查证、跨路由与重新打开页面后状态可恢复；不同故事不串状态；故事变短后旧段号能安全裁剪；本地数据损坏或不可写时仍可正常阅读；用户可以清除本功能保存的数据。

### R13 · 参考文本来源与下载结果可复现（P2）

**位置**：`web/scripts/fetch-refs.mjs`、`refs.json`、`check-sources.mjs` 及必要的来源清单。

**问题**：参考文本使用移动分支等可变化地址，缺少固定版本与内容校验值，未来重新下载不保证得到当时核对的文本。既有校勘规则也必须继续可追溯。

**修改要求**：记录来源 URL、固定修订（适用时）、实际文件哈希及获取/核对信息。版本变化明确报告，不静默替换核对基准。检查断点下载的 HTTP 状态：服务器忽略 Range 返回 200 时，不得把完整文件反复追加；对下载完成和参考范围做真实验证。下载、合并与验证均使用项目正常入口，保留用户已有参考文件，避免未经备份覆盖。

**验收**：相同固定版本可重复获取并验证；内容变更或不完整能明确失败；正常下载的文件不会因重试而重复增长；现有登记校勘仍生效。输出只能证明与指定电子本一致，不宣称达到权威版本校勘或历史事实全真。

## 4. 架构方向：本轮适度实施

以下是设计方向，按 R01—R13 的实际需要渐进落地：

- 区分文献类型、转引关系、原文、译文、历史主张和可信程度。
- 为高风险内容采用显式块类型，减少靠引号、标题和字符猜结构。
- 将编译器的解析、模型、规则、输出职责逐步分开，统一可见字段遍历。
- 稳定内容 ID 与显示顺序逐步分离。

本轮不要求迁移全库格式、建立通用知识图谱、重写全部编译器或增加所有人物生平。保留已成立的暗场、纸面、字体和朱批视觉语言。

## 5. 研发约束与交付要求

### 工作区与副作用

1. 先阅读适用的 `AGENTS.md`、用户数据库安全规则及现行内容规范，检查 `git status`。保留已有未提交工作，包括本任务书和原评估文档。
