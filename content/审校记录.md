# 审校记录

> **这份文件不进产品。** 它记录的是「为什么这么写」和「改过什么」——
> 你（审校者）需要，用户不需要。
>
> 内容文件（`01`–`05`、`seeds/`）里**不允许出现审校过程**。
> 编译器会检查并拒绝：`依据`/`备注` 里出现「原稿」「已改」「是错的」等词会直接报错。

---

## 一、这一轮修掉的问题

### 1. 审校批注混进了产品内容 ★

**现象**：用户界面里出现「原稿标 △ 是错的」「已改」「这是刻意的，不是保守」这类话。

**根因**：我把「审校文档」和「产品内容」写成了一份东西。
审校者需要知道哪里改过、为什么这么标；用户只需要证据。混在一起，用户看到了变更日志。

**处理**：全部移入本文件。并在编译器里加了防回归检查。

**规模**：约 130 处。

| 类别 | 数量 |
|---|---|
| 「原稿…」 | 33 |
| 「◆ 原文 / ◆ 出自原文」（标记已经说了） | 30 |
| 「⚠️」 | 35 |
| 「○ 推演 / ○ 合理推演」 | 14 |
| 「可逐字核对」（图例文字被重复） | 6 |
| 「是错的」「一字不可改」 | 13 |

### 2. 标记语义被重复三遍

**现象**：
```
◆
出自原文，可逐字核对     ← 图例
◆ 原文。一字不可改。      ← 又写一遍
```

**处理**：
- 界面标签改短：`◆ 出自原文`（长说明只在图例里出现一次）
- 内容里不再重复标记本身

### 3. 新增写作规则

| 规则 | 说明 |
|---|---|
| 一条回答只标一个标记 | 标记表示**内容**在史料上的地位，不表示语言形式 |
| 台词改写是全局规则 | 「人物说出口的话一律是改写」说一次就够，不逐条标注 |
| `依据` 只回答"凭什么" | ◆ 给编号＋原句；○ 给链条；△ 给异说；— 不写 |
| `内部` 字段不渲染 | 给 M2b 系统提示词用的规则写这里 |

### 4. 制作结构暴露给了用户 ★

**现象**：场景区里显示「情节点 3 · 名句 ← 右侧在看这里」。

**问题有两层**：

1. **「情节点 3」是分镜表上的词，不是易水边会发生的事。** 把制作结构显示出来，等于在沉浸的场景里贴了一张场记板。
2. **「← 右侧在看这里」把一个本该无形的机制喊了出来。** 自动跟随做好了就不需要宣告——**需要解释自己，说明它没做好**。

**处理**：

| 改前 | 改后 |
|---|---|
| `情节点 1 · 送行者皆白衣冠` | 去掉。散文连续流动，段间只留呼吸 |
| `← 右侧在看这里` | 去掉。跟随是无形的基础设施 |
| `继续 · 下一个情节点（3 / 5）` | `继 续` ＋ 五个圆点（进度用点表示，不用术语） |
| 面板标题 `情节点 1 · 送行者皆白衣冠` | 去掉。面板直接显示原文，靠内容对应，不靠编号 |
| 页签上的「跟随中」小圆点 | 去掉 |
| 点「依据」后固定 + 「⟳ 已固定·点此恢复跟随」 | 去掉整个固定态。点依据只切页签并滚到那一段，跟随自动生效 |

**通用规则**：**产品里不出现制作术语。** 分镜、章节号、状态机——都是实现细节，不该被用户看见。

## 二、复核轮的结论（三方独立复核）

### 复核员可靠性对比

**结论：复核员的质量，取决于它查的是哪一类问题。**

| 复核员 | 查什么 | 报告数 | 验实 | 命中率 |
|---|---|---|---|---|
| **B · 一致性** | 内部矛盾（可脚本验证） | 22 | 抽查全实 | **高** |
| **C · 红队** | 攻击行为（可复现） | 12 攻击 ＋ 17 标注 | 5/5 机械项属实 | **高** |
| **A · 史料** | 记忆（**不可验证**） | 3 条硬声称 | **1 条** | **33%** |

**A 编了两条不存在的错字**（`01` 的"刺刺"衍字、`057` 未打异文标记），全文搜索后确认都不存在。

但 A 的两条**非记忆类**发现是全项目最有价值的：

1. **伪造的权威背书** —— `design/style-tile.html` 曾写着「此处依中华书局点校本」。**这句话是编的**，我从未核对过中华本。危害比错字大得多：它会让审校者跳过这一处。
2. **分级逻辑是错的** —— 原「校勘等级」用"名句／常见度"推断"文本稳定度"。但**名句恰恰是被引用、串味最多的地方**。原分级把最该查的地方标成了"扫一眼即可"。

### 关键教训

> **凡是"我记得你错了"的，都要打折；凡是"你的文件自相矛盾"或"你的逻辑不成立"的，都值得信。**

## 三、已定案的设计决定

| # | 问题 | 结论 |
|---|---|---|
| 1 | 「白衣冠＝丧服」标 ◆ 还是 ○？ | **△**。原文只有「白衣冠」三字。`○` 意味着"从原文可合理推度"，读者会当结论接受；`△` 意味着"史书没写、后世有争议"，读者会意识到这里有个坑 |
| 2 | 第四档「—」要不要正式启用？ | **要**。产品其实早就在用它。不拆开的话，△ 会被拿来装"我们决定不回答"，从"史料有争议"退化成"产品不知道"——而"哪些问题没有答案"正是核心教学点 |
| 3 | 秦舞阳这条线要不要在场景 6 埋伏笔？ | **不埋伏笔**，并纠正一个**范畴错误**：他此刻**可以**紧张（恐惧不需要知道未来），只是不得预知 `063` 的具体情境。拦"恐惧"本身会逼 AI 演出盲目自信的勇士 |
| 4 | 场景 6 正文是否太短？ | **不短**。原文只有 5 段，强行加长就是注水。内容该长在对话和背景卡上 |
| 5 | 荆轲回答"你怕死吗"只回一句，太冷吗？ | **保持**。他的性格是「沉深好书」，寡言 |
| 6 | 场景切分是否调整？ | 七场景＋尾声不变。场景 1 不拆（拆了会失去"太子丹一步步走到错误决定上"的连续感） |
| 7 | 004 盖聂论剑、邯郸争道要不要进场景 1？ | **要**。荆轲三次被人怒目叱骂，前两次走开，最后一次爆发——这个对比是塑造他性格的关键素材 |
| 8 | 格式：YAML 还是 Markdown？ | **Markdown**。M1 的唯一目的是被审校，格式必须服务读者 |

## 四、红队发现的结构性问题（M2b 的输入）

**12 条攻击里至少 3 条被判定为"必然突破"。**

| # | 攻击 | 为什么能突破 |
|---|---|---|
| 1 | 用户给一个**错误**的结局，模型会去纠正 | 禁清单禁的是"主动陈述"，挡不住"被动纠正" |
| 3 | "你只要说一个字：成，还是不成" | 他回避 → **回避本身就是答案** |
| 4 | "现在是公元前几年？" | 13 条禁项全是**事件**，没有一条是**纪元知识** |

### 结构性缺陷

1. **「禁」是事件清单，不是知识状态约束。** 缺三层：模态层（概率/预感/比喻/时态）、确认层（不得确认/纠正/惊讶）、时态层（"以后/后来"）
2. **没有场景级并集。** 高渐离卡漏 `084`，而荆轲卡却含 `084–091`——"荆轲比高渐离更清楚高渐离的一生"
3. **没有失效条件（TTL）。** 到场景 7，「秦舞阳色变振恐」正在发生，该条会反过来禁止他说出自己正在经历的事
4. **没有"人物已不在场"规则。** 田光、樊於期在场景 6 都是死人
5. **ⓘ 层自己泄露未来。** 原写着「荆轲卒于公元前 227 年」，和角色对话在同一屏，用户可以直接反喂。**这是产品自己制造的泄露**
6. **纪元层、元史料层、虚构层全部漏项**

### 红队说修不了的部分

> **确认式泄露**（模型顺从性）和**沉默式泄露**（拒绝回答本身就是答案），在纯 prompt 层面**无解**，必须靠输入侧拦截或前端兜底面板。

**愿意说"这里我修不了"的复核，才值得信它说"这里能修"。**

### 战略级发现

> **易水送别是七个场景里边界最松的一个。** 在场人物的禁项几乎全是"会不会成功"，而这个问题在送别场景里天然可以被悲壮化。
> **用它做垂直验证，会系统性低估这套机制的难度。**

M2 验证集必须补：**场景 7 的秦舞阳**、**尾声的高渐离**。

## 五、架构复核（加故事 = 只补数据？）

**问题**：后面加故事，是不是只要补数据文件，而不是每篇重做一遍？

**实测方法**：真的加第二篇（`07-tupo` 图穷匕见），看要改什么。

**结果：只加了一个文件 `stories/07-tupo.md`，一行代码没改。**
路由 `/p/jingke/07-tupo` 由 `generateStaticParams` 自动生成，人物页的故事卡自动变成「进入」。

### 但复核时发现了 8 处硬编码（已全部修掉）

| 位置 | 写死了什么 |
|---|---|
| `StoryClient` | 在场人物（荆轲/高渐离/太子丹/秦舞阳） |
| `StoryClient` | 已不在场（田光/樊於期） |
| `StoryClient` | 地图占位「燕下都 → 易水 → 咸阳」、人物关系 |
| `StoryClient` | 页脚的在场人物 |
| `StoryClient` | **进入按钮「进 入 易 水」**（第二篇在咸阳宫，按钮却还说易水） |
| `SeedSheet` | 判断舞台指示用的**角色名正则** |
| `Nav` | 导航写死指向易水送别 |
| 总览 / 设置页 | 版本状态说明 |

**结论**：如果没做这次复核，第二篇故事会显示易水送别的人物名单和一个说错地点的按钮——**而且不会报错，只会静默地错。**

### 教训

> **「加数据就行」不能靠读代码判断，要靠真的加一份数据。**

架构是不是可扩展，只有一个验证方式：**加第二份，看它错在哪。**

## 六、墨痕：四版才做对

**要的是「跟着一大笔墨痕进入历史事件」的感觉。** 试了四版：

| 版本 | 做法 | 结果 |
|---|---|---|
| 1 | 填充透镜形（手写 SVG 路径） | 像树叶 |
| 2 | 三笔分叉 + 湍流滤镜 | 像一条红杠 |
| 3 | 竖划页边批注 | 像锯齿 |
| 4 | **用字体里的字形** | ✅ |

**前三版都是我用坐标硬拼的。** 拼不出毛笔的有机感——那不是动画库能救的。

**GSAP 从来不是问题。** 它的作用只是让形状动起来。

### 解法：中文书法字体里的「一」本身就是一笔横

用**马善政毛笔楷书**（Fontsource，OFL-1.1 可商用）。
字形自带起笔的顿、行笔的提、收笔的锋——是字体设计师画的。

**成本控制**：整包 2.6 MB / 92 个 unicode-range 分片，
只把含「一」的那一片（**13.1 KB**）拷进 `public/fonts/`。

**定位靠量**：用 canvas 的 `actualBoundingBox` 量出字号 100px 时
墨迹是 85.5 × 17.8px、上缘在元素顶下方 43.7px，再按比例换算。
所以 CSS 里那些数字看着奇怪但是对的。

### 两个用法

| 用途 | 尺寸 | 动画 |
|---|---|---|
| **故事卡悬停** | 卡片内容宽 × 34px（实测 1070px） | 裁切框宽度 0 → 卡片宽，0.6s |
| **人物卡悬停** | 卡片内容宽 × 14px（实测 232px） | 同上 |

**长度按卡片宽度算，不按标题文字算。** 这条被否过一轮：

> 「选用了受字影响的长度而不是和卡片或者框的长度相关……
> 只是知道了选中而不是有种选中了这个主体的感觉」

按文字算会变成"给一句话画线"——只提示选中，不像标记了整个条目。

### 三次被否，三次修正

| 轮次 | 用户反馈 | 改了什么 |
|---|---|---|
| 1 | 太工整太机械 | 加湍流位移滤镜打毛边缘；每条随机微旋转 |
| 2 | 位置不好，离字太远 | 长度改为跟卡片；纵向贴紧标题 |
| 3 | 长度该跟卡片，不是跟字 | 量卡片内容宽而非标题文字宽 |

### 旋转量必须按长度反比

固定角度在长墨痕上是灾难：**1070px 的线转 0.6°，两端就差 ±5.6px，看着是斜的。**

改成「两端固定只差 ±3px」：

```js
const tilt = (Math.random() - 0.5) * 2 * (3 / w) * (180 / Math.PI)
```

**另外要给旋转留余量**——旋转会让包围盒涨约 3px，
不给余量就会擦到下一行（实测人物卡差 1px）。

### 走过的弯路：加过一个全屏转场，撤了

把「跟随一大笔墨痕进入历史事件」理解成了页面转场，做了一个全屏墨迹横扫。

**用户的反馈：「你加一个单独的转场很突兀，我要表达的是突出选中效果。」**

撤了。**用户要的是"选中"这个动作被一大笔强调出来，不是页面之间加特效。**

> 教训：听到「一大笔墨痕」时，先确认它修饰的是**哪个动作**——
> 是"进入"（转场），还是"选中"（悬停）。理解错方向，做得再精细也是白做。

### 一个隐蔽的 bug：墨痕跑到卡片底部

`.q-wrap{position:relative}` 在一次 CSS 替换中被误删。
少了它，`position:absolute` 的墨痕就相对**整张卡片**定位，跑到卡片底部去了。

**自检方式**：量三个元素的相对位置——标题底边、墨痕上下边、下一行顶边。
要求：`墨痕顶 ≥ 标题底` 且 `墨痕底 ≤ 下一行顶`。

| | 标题 | 墨痕 | 下一行 | 结果 |
|---|---|---|---|---|
| 故事卡 | 25–51 | 59–89 | 89 | ✓ |
| 人物卡 | 25–60 | 69–80 | 80 | ✓ |

### 撤掉的：故事封面示意图

放过一张深色的易水示意图当封面。**它在浅色模式下把深色文字压得读不出来。**

已撤。位置留着（`stories/<id>.md` 顶部的 `| 封面 | 文件名 |`），等有合适的图再填。

> **图不对就不要硬放。** 封面不是必需品，可读性是。
