### 为什么闸门从第一步挪到第三步

第一版把闸门排第一，理由是「它保护后面所有活」。**审核指出它防的是没发生过的失败模式：**

- 闸门要抓的是「**范围变了、话没跟着变**」
- 但今天真正造成损坏的机制是「**范围没变、正文被改坏**」
  （`031–033` 还是 `031–033`，戳对得上，闸门全绿）
- 而它现在唯一能报的红（08-guandu）恰好是第 1 步要修的东西

**先跑顺两篇，再决定闸门要拦什么。**

### 闸门怎么做（第一版的设计有循环，审核给了更好的）

第一版设计：文件顶部写一行「本文件对着的范围：…」，编译器拿它和故事一览比。
**循环**：④ 的完成标准是「闸门归绿」，而 ④ 的活就是改那一行——**同一只手既改范围、
又改声明、又是唯一判定归绿的人**。而且它要动 36 个文件，不是「不改任何内容」。

**改成「查事件」**（审核的做法甲，0 个内容文件改动）：
> `stories.md` 的「原文」列**在本次改动里变了**、而 `seeds/<id>.md` 与 `cards/<id>.md`
> **没跟着变** → 红。

它查的是「范围变了吗」，不是「你自己声明的范围对不对」——**没有可以被改绿的自述字段**。
唯一能让它闭嘴的动作，就是真的在同一个提交里动那个种子文件，**而它会出现在 diff 里**。

再加一条：范围变了的提交里，`seeds/<id>.md` 的**非声明内容也必须有实质改动**，
否则报「你只改了声明，没重读」。

**并且把「无编号的读者可见文字」纳入扫描**：现在 `sweep()` 只看「依据/备注」两栏，
`内部`、围栏 ⓘ、卡片「考点/说明」全在外面——**今天找到的 10 处旧编号，0 处在被扫范围内。**

## 四之补、一条我犯过三次的错（写在这里，因为它只能靠习惯防）

**`git add -A` 会把工作区里所有东西一起收，包括正在跑的子智能体的中间态。**
2026-10-15 我犯了**三次**：

| 次 | 后果 | 怎么修的 |
|---|---|---|
| 1 | `10-weiwang.md` 的半成品进了提交 | `git reset --soft HEAD~1` 摘出来重提 |
| 2 | `10-weiwang` 的标记分布表被提交成红的（它在我跑完 check 之后又改了一处） | 收下它的修正，另提交 |
| 3 | `01-wusebang.md` 的半成品进了提交（**又是 `git add -A`**） | 同上，`reset --soft` 摘出来 |

**共同点：我在子智能体还没报「做完了」的时候就提交了。**

**规矩（从这一条起执行）：**

```
① 子智能体报「做完了」之后再提交它的文件。在那之前不碰。
② **按路径 `git add <文件>`，不用 `git add -A`。**
   —— 这一条是机械的：`-A` 在任何时候都会收别人的东西，而不只是在有子智能体的时候。
③ 提交前 `git status` 看一遍：多出来的文件是不是我的。
```

（`reset --soft` 是对的恢复动作：它只动 HEAD 和索引，**不碰工作区**，
所以别人的半成品原样留着。）

## 四之补二、范围变更闸门的一个已知弱点（子智能体查出来的）

`05-yanzhou` 的子智能体报：**HEAD 上账本里 `01-wusebang` 的指纹是旧的**
（账本记 `f0fd50c9…`、实际 `3da1234f…`）。**后果：那一篇的范围闸门是哑的**——
范围一变、而「账本记的指纹」和「现在的指纹」本来就不相等，
闸门会把它读成「内容变过了，人重读过了」，于是不响。

**成因**：账本由任何一次**非 `--check`** 的编译写入。我在子智能体还在改的时候
跑过 `npm run content`，就把中间态的指纹记了进去；它随后又改了文件，账本就旧了。

**这不是能靠设计完全消掉的**：指纹分不出「范围变之前就改过」和
「跟着范围一起改的」。所以：

```
① 内容定稿（子智能体报完成、提交）之后，跑一次 npm run content 刷新账本，并提交它。
   —— 账本新鲜时闸门是armed的；旧的时候对这一篇是哑的。
② 每次刷新会自愈：跑过一次之后，那一篇又armed了。
③ **不要指望它替你抓所有情况**——它是第二道网，第一道永远是「范围变了就重读」这个动作。
```

（本轮已经跑过、提交了：`01-wusebang` 与 `05-yanzhou` 的指纹现在都对得上。）

```
① 跑批量脚本之前先提交。工作区必须干净 —— **已经是代码**（guard.mjs）
   已接进 renumber.mjs；双向验过：脏了拦、干净放行

③ 批量脚本必须能连跑两遍：干净树上跑第二遍，git status 必须为空
   （这条是第一版没有的决定性验法——「幂等」不能只是意愿）
④ 批量脚本先空跑，把「会改什么」打出来
   但要机械化一条：重编号只许改「原文」列和三位编号，
   **时间/年份列动一个就停**（今天赤壁的 208 被当成编号改成了 408）
⑤ 一篇（一段、一批）一个提交 —— 不做「攒着一起提」
⑥ 恢复动作是 **`git revert`**，不是 `git reset`
   （今天丢东西的就是 reset 的同类命令：它动工作区，会带走未提交的活）
```

**「损失 ≤ 一个提交」这个承诺不成立**，改成它实际能保证的：

> **每个提交点都能退回。语义错误不在此列——那是 08-guandu 教给我们的：
> 它的种子卡早就提交了，check 一直绿，而它说的是假话。**

## 七、第一版错在哪（留着）

独立审核否掉第一版的理由，按重要性：

1. **第一节「你可以自己验」里有三个数是错的**，其中一个（`不连续 0`）是脚本
   **根本不会打印**的东西。这一节的全部意义就是让你能自己验；**它自己先没验。**
   在今天已经犯了三个错的语境里，这是**同一个毛病的第四次**。
2. **它把唯一一条自称已上线的机械保障说成「已经是代码」——那一行是死的。**
   （`guard.mjs` 全仓无人 import。）这条如果没被查出来，你会以为有人守着。
3. **「已知的坏东西」只列了一条，实际同类至少五类**，分布在另外四篇上。
   第②步会做完就宣布这块地干净了，而残渣还在原地。
4. **闸门有一个循环**，而且防的是没发生过的失败模式，还排在真正要修的东西前面。
5. **验证方式和失败模式不匹配**：拿截图验种子卡的真假，而那些假话一个字都不渲染。
6. **顺序**把你要的东西（故事不简陋）排在第三位，排在它前面的闸门做完之后
   唯一的红灯就是第二步要修的东西。

**共同点：这份计划的形式是可信的（每步都有「你怎么验」、有负向测试、有不做清单），
但它的内容没经过它自己要求的那种核对。今天三个错的共同点是「以为已经好了」；
这份计划的第一节就是同一个东西。**
